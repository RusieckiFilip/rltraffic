## 1. What this task measures, and what it must not conclude

One question, one number per cell:

> **Do the offline-learned policies admit fewer vehicles into the network than the behaviour policy of
> their own tier?**

`metrics/cityflow.py::average_travel_time` averages over vehicles the metric has *seen running*
(`get_vehicles(include_waiting=False)`, `:60` and `:159`). CityFlow's own `getAverageTravelTime`
(`engine.cpp:682-691`) averages over the whole `vehiclePool`, i.e. every vehicle ever created. A policy
that keeps vehicles in the lane insertion buffer therefore shrinks our metric's denominator *and* drops
its slowest members. T1 measured 774/2021 (38.3 %) never admitted under `random` on hz1x1.

**This task measures admission. It does not fix the metric, does not re-derive ATT for the paper
(that is P8.4b), and its artifact carries no verdict on P5.2's headline** (`BRIEF_31` §6).

⛔ The packet may not say *"the metric is wrong"*. It computes what its docstring says. **It measures a
different population than the field's, and that is the finding.**

## 2. The instrument

### 2.1 The rollout is P4/P5's, reused byte-for-byte

Every episode goes through `offline.horizon_metric.horizon_rollout` — the same function
`offline.dt_gate.evaluate_arm` calls — with the same env construction (`experiments.envs.make_env` +
`EnvSpec`), the same settings source (`dt_gate.env_settings_from_manifest` on the tier's own collection
manifest), the same `engine_seed`, the same action factories (`_maxpressure_factory`, `_mappo_factory`,
`_random_factory`, `_fixedtime_factory`, `_baseline_factory`, `_dt_factory`, `SpatialDTAgent`).

**Nothing about the episode changes.** The probe reads the engine and the metrics object *after*
`horizon_rollout` returns and *before* `env.close()`. No extra `next_step`, no subclass, no monkeypatch,
no per-second sampling. This is why the reproduction check in §2.4 can be exact.

`offline/horizon_metric.py` is **not modified**. `evaluate_arm` is **not modified** — it closes its env
in a `finally`, so the probe owns its own loop, which is a copy of `evaluate_arm`'s body plus the four
post-rollout reads. That duplication is deliberate and is disclosed in the module docstring.

### 2.2 The five quantities, per episode

| field | source | kind |
|---|---|---|
| `att_ours` | `rollout.per_episode_horizon[0]` | the A1 primary metric at the horizon |
| `att_engine` | `env._eng.get_average_travel_time()` after the rollout | CityFlow's own definition |
| `horizon_vehicle_count` | `rollout.final_vehicle_count` | already reported by P4/P5 |
| `created` | see §2.3 | denominator, fixed per draw |
| `entered` | see §2.3 | numerator |

plus `never_entered = created - entered`, `entered_fraction = entered / created`,
`completed_at_horizon`, `waiting_at_horizon`, and `seconds`.

### 2.3 `created` and `entered` are each computed by two independent routes and asserted equal

Read from `CityFlow/src/engine/engine.cpp` in this session:

* `activeVehicleCount` is incremented **only** in `handleWaiting()` (`:509`), when a vehicle leaves a
  lane's waiting buffer and starts running, and decremented **only** at `:309`, when it finishes.
* `getRunningVehicles(includeWaiting)` (`:780-789`) walks `vehiclePool` and keeps
  `isReal() && (includeWaiting || isRunning())`. `laneChange: false` in every draw config, so `isReal()`
  is inert here.
* A vehicle enters `vehiclePool` at creation (`pushVehicle`, `:605-613`) and is erased only when it
  finishes (`:308`).

Therefore, at the horizon:

```
never_entered = |get_vehicles(include_waiting=True)| - |get_vehicles(include_waiting=False)|      (R1)
entered       = |metrics._episode["depart_time"]|                                                 (R2)
entered       = |metrics._episode["completed"]| + |get_vehicles(include_waiting=False)|           (R3)
created       = entered + never_entered                                                           (R4)
created       = #{flow entries with startTime <= max_steps*delta_time - 1}                        (R5)
```

**R1 is engine-side and exact. R2/R3 are metric-side.** R5 is the flow file parsed independently of the
engine; it is exact for this corpus because **every flow entry in every materialised draw has
`startTime == endTime`** (verified this session on `cityflow1x1/draw_1000`: 1821 entries, all
`start == end`, all `interval == 5`; `cityflow_grid4x4/draw_1000`: 1323 entries, same shape), and
`Flow::nextStep` (`CityFlow/src/flow/flow.cpp:6-22`) then emits **exactly one** vehicle, at
`currentTime == startTime`, provided `startTime <= n_engine_steps - 1`.

⚠️ **The bound in R5 is load-bearing and is not cosmetic:** `cityflow1x1/draw_1000` has
`max startTime = 3658` against a 3600-step episode, so **8 of its 1821 flow entries never fire**.
Reading `provenance.json`'s `n_vehicles` (1821) as `created` would be wrong by 8 vehicles.

**The probe asserts `R2 == R3` and `R4 == R5` with `==` on Python `int`s, per episode.** A mismatch
raises and the episode is not recorded. `entered` is then reported from R4/R5's agreed `created` minus
R1's `never_entered`.

## 4. Registered scoring rules — written before any campaign number exists

Per cell, per seed, over the cell's ten shared draws:

```
r(arm, tier, seed) = sum_draws entered / sum_draws created          # a population ratio,
                                                                    # not a mean of ratios
r(arm, tier)       = sum_{seed,draw} entered / sum_{seed,draw} created
spread(arm, tier)  = max_seed r - min_seed r                        # 0 for a single-seeded arm
```

Per-seed values are **always** reported; the pooled `r` is a summary and never replaces them
(`BRIEF_31` §5).

### E1 — the load-bearing prediction

```
deficit(arm, tier) = r(behaviour, tier) - r(arm, tier)
Delta(arm, tier)   = max( spread(behaviour, tier), spread(arm, tier) )

deficit <= 0            -> E1 HOLDS for that arm
0 < deficit <= Delta    -> CLOSE
deficit > Delta         -> E1 FALSIFIED for that arm
```

**Escalation, registered now:** *any* arm with `deficit > 0` — close **or** falsified — is re-run at the
full 100 held-out draws before anything is said about it. `deficit == 0` exactly (both sides at full
admission) is **not** closeness and does not escalate; exact equality is a result.

Reported alongside, never instead of: the **paired per-draw** difference
`entered_arm(seed, draw) - entered_behaviour(seed, draw)` and its mean with a 95 % CI, over the shared
`(seed, draw)` pairs. For a single-seeded anchor the same anchor episode pairs against all five arm
seeds, and that is stated in the artifact.

### E2 — the null control

`mappo1000`'s arms sit at `r ≈ 1.0`. **Registered band: `r >= 0.99` for every `mappo1000` arm on both
scenarios.** Anything below indicts the probe before the science.

### E3 — the instrument control, and its domain is fixed HERE

T1 measured 100.0 / 90.8 / 92.9 / 65.0 % for `mappo1000` / `fixedtime` / `mappo060` / `random` **on
hz1x1**. Two mismatches with this repo, both recorded in §5:

* `mappo060` is **not** a P4.6 tier; P4.6's five are `mappo1000`, `mappo500`, `maxpressure`,
  `fixedtime`, `random`.
* T1 measured **training** draws with the **corpus** behaviour policies; we measure **held-out** draws
  1000–1009 with the behaviour policies **re-rolled**.

**Therefore: E3 is scored on the five hz1x1 behaviour anchors only.** The registered form is
`r(behaviour, mappo1000) > r(behaviour, random)`, with the full five-tier profile reported.

🔒 **grid4x4's behaviour profile is reported and is NOT scored against E3.** This is registered before
the campaign because exploration already showed zero censoring on one grid4x4 draw (§2.4): a flat
grid4x4 profile is a scenario difference and **must not** be read as the "flat profile" that E3 names
as indicting the replay, because E3's falsifier was written against an hz1x1 measurement. Reversing
that inference after the fact is exactly the move `BRIEF_31` §2 forbids.
