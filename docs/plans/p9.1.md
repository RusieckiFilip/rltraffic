## 2. Numbered open questions — the build stops ONLY on these items

**Q1 — which episode index seeds the `per-episode` generator.** A27(d) writes
`np.random.default_rng([base_seed, draw_id, episode_index])`. `collect.main` has two candidates:

- the episode's index **within its draw** (`index`, the loop variable that already gives `engine_seed = base_seed + index`);
- a **run-global** counter (`episode_index`, which `ep%06d` file names also count).

Implemented: the within-draw index. The schedule is then a function of `(base_seed, draw_id, episode-within-draw)`
alone. Any subset run regenerates it, and the brief's test wording ("two runs of the same (draw, episode) must be
identical") reads naturally. With `--episodes 1` the two readings give different, equally distinct corpora
(`[1000, d, 0]` against `[1000, d, d-1]`). **Nothing is collected before G3, and P9.3's hz4x4 random tier inherits
this.** The coordinator should rule before M1 merges if the global counter was meant.

**Q2 — `random_fresh`'s hz1x1 prompt cannot be typed before collection (K3).** Proposed:

1. The campaign's first stage collects the two `random_fresh` tiers and runs `declare` under its own token. That is CPU
   only, about 400 episodes, roughly 10 minutes.
2. A reviewed commit types the hz1x1 `target_rtg` / `rtg_scale` from the declaration, with a corpus-gated test that
   re-derives them from the raw `.npz`.
3. The training and evaluation stage runs under a second token.

The alternative is a rule-resolved spec, values computed from the corpus at run time and pinned through the
declaration's digest. It touches `att_rederivation.build_cell_factory`'s use of `TIERS[tier].target_rtg` and the DT
factory, so it is not proposed. Until the typed commit, EVERY hz1x1 `random_fresh` arm is refused:

## 3. Design decisions (not stops; each is written into the artifact that depends on it)

**D1 — arm names are derived from the flags, never typed by hand.** One registry in `offline/corrective_round.py` maps
every A27 arm to `(scenario, base method, batch, target_dropout, steps)`. A training CLI derives the arm name from its
flags and refuses any combination the registry does not declare. Examples of refusals:

- `iql` at 20,480 transitions with active targets;
- `bc` at 102 windows;
- any hz1x1 batch other than the registered one (A27(b): no hz1x1 exposure arms);
- `iql_t` at 100,000 steps (A27(g)).

A registered name trained at 100,000 steps is impossible by construction, and the registry check refuses it explicitly
(the brief's test). Names:

- hz1x1: `iql_t`, `dt_100k`, `bc_100k`, `bc_top10_100k`, `iql_100k`;
- grid: `bc_m` (1,024 windows), `bc_top10_m` and `bc_top10_perix_m` (102), `iql_m` (20,480, targets off), `iql_t`
  (1,280, targets off);
- on `random_fresh` and `mix_m1000_m500` the registered recipes keep their registered names (`dt`, `bc`, `bc_top10`,
  `iql`, `dt_nomix`): the tier name is what is new.

**D2 — the fresh random reference** is arm `random_fresh@random_fresh` on each scenario. Method `random_fresh` follows
P5.1's precedent of `random` being both a method and a tier name. Its generator is `default_rng([seed, draw_id])`.
Rollouts hand the factory an env only. The factory therefore recovers the draw by exact lookup: the env's resolved config
path must equal `draw_config_path(scenario_key, d)` for exactly one held-out `d`, otherwise it refuses. It reads
`CityFlowEnv._config_path`, which is private, and the docstring says so. The registered five-schedule reference stays
`method_tier_grid._random_factory(seed)`, unchanged.

**D3 — old cells (K7).**

- **Grid old cells** are loaded through `tier_statements.load_inputs`. That is P5.2c's pinned loader, the route that built
  the committed `p5_2_statements.json`, so it is the committed artifact's own route. It covers every P5.1/P5.2 cell under
  both definitions, with `iql@random` as P5.2b's corrected cell beside P5.2's original.
- **hz1x1 old cells** are re-rolled through P8.4b's route (`att_rederivation.run_campaign`, default factory builder,
  `--output-root` the main tree). `committed` is each cell's own artifact: `p4_4_baselines.json`, `p4_6_grid.json`,
  `p4_7_grid.json`, `p4_gate.json`. Each episode's `att_ours` must reproduce under `==`, otherwise the cell is refused.
  This includes the four P8.4b did re-derive, because a re-roll costs minutes and leaves no reliance on an unmanifested
  tree.
- **Seconds and steps** of every compared old run come from the committed training records (`p4_training.json`,
  `p4_4_training.json`, `p4_6_training.json`, `p4_7_training.json`, `p5_2b_iql_correction.json`) or, where only a
  checkpoint holds them (P5.1/P5.2 grid baselines), from `provenance.gradient_steps` with `seconds: null` and the
  reason.

**D4 — route (i) for new cells** is the module CLIs' own `evaluate`, in process, with their new A27 wiring:
`method_tier_grid.main([... "evaluate" ...])` for hz1x1 and `tier_sweep.main([... "evaluate" ...])` for the grid, as P5.2b
did. The hz1x1 CLI reads a training record in its own format. The campaign therefore writes
`output/p9_1/p9_1_training.json` (40,000 steps) and `output/p9_1/p9_1_100k_training.json` (100,000 steps), regenerated
from the per-run records on disk. Route (ii) is `att_rederivation.run_campaign` with `committed` = route (i)'s per-episode
`att_horizon` (`iql_correction.committed_from_eval`'s construction). A disagreement is a refusal and stops the campaign.
For new arms the factory comes from an injected builder (§4.5).

**D5 — P3a's action sequences** come from a third, recording pass over the cells it reads:

- `dt@random_fresh` (hz1x1) and `dt_nomix@random_fresh` (grid);
- both random references on both scenarios.

The pass uses `dt_gate.evaluate_arm` with the route-(i) factory wrapped by `nortg_decomposition.recording_factory`. Each
episode's `att_horizon` must equal route (i)'s under `==`, so the recorded trajectory is the reported one. The registered
five-schedule reference is re-rolled this way too; its `att_ours` must reproduce the committed one.

**D6 — training is direct, not through the CLIs.** The campaign calls `train_bc` / `train_iql` / `train_dt` /
`tier_sweep.train_tier_dt` on inputs built by the modules' own helpers. Those are:

- grid: `tier_parts`, `baseline_stream_selections`, `iql_transition_table`;
- hz1x1: `tier_dataset`, `training_streams`, `top_decile_streams`, `filter_stacked_to_streams`, `build_transitions`,
  `filter_transitions_to_streams`.

This is the P5.2b precedent: the CLIs train every seed of every method per call and are not resumable per run. T-train-args
tests prove that the campaign and the CLI hand each trainer identical arguments and tensors. Each run trains into
`<name>.partial`, is checked, then moved. Its write-once record holds `seconds`, `gradient_steps`, the canonical and file
digests and the full provenance. Status is computed from disk.

## 4. The build, commit by commit

### C1 — `offline/offline_baselines.py`: `train_iql(..., target_dropout="active")`

- `target_dropout ∈ {"active", "off"}`, validated before anything is created; anything else raises.
- **`"active"` is the registered path, unchanged statement for statement.** The only refactor is a module-level seam,
  `_awr_weight(q_taken, v_baseline)`, which holds the two registered lines (`advantage = q_taken - v_baseline`,
  `clamp(exp(β·adv), max=clip)`) under `no_grad`. Under `"active"` it is called with `v_pred.detach()`, exactly as today:
  same operations, same tensors.
- **`"off"`** changes three forwards, each followed immediately by a return to `train()`:
  - `q_target.eval()` → `q_target(s)` under `no_grad`;
  - `value.eval()` → the advantage's `value(s)` as a separate `no_grad` forward, BEFORE `optimisers["v"].step()` (so the
    registered update order is kept: V before its update);
  - `value.eval()` → `value(s')` for the TD target.
  The trained forwards (`value(s)` for the expectile loss, `q(s)`, `policy(s)`) run in `train()`.
- `target_dropout` is recorded in the checkpoint provenance and in the diagnostics (both modes). The trained tensors under
  `"active"` are unchanged.
- **Test seam — forward hooks, no further refactor.** The test replaces `offline_baselines.MLPTrunk`, which `train_iql`
  resolves at call time, with a constructor that builds the real module and registers a forward pre-hook. The hook
  records `module.training`, a digest of the module's parameters, and the output. The role comes from construction order
  (policy, q, value, q_target), which is part of the registered code because initialisation consumes the RNG in that
  order. `_awr_weight` is spied to capture the V the advantage actually used.
- **Tests (`tests/test_iql_target_dropout.py`), written first:**
  - under `"off"` the three target forwards record `False` and the three trained forwards `True`;
  - under `"active"` all five forwards record `True`;
  - both modes: the advantage's V comes from the pre-update parameters, compared against the parameter digest after the
    V step and against an eval-mode V forward taken after the step;
  - under `"off"` the advantage's V is bitwise the eval forward's output;
  - the modules are back in `train()` after the forwards (a two-step run catches a missing restore);
  - provenance and diagnostics record the flag;
  - a bad value is refused before the checkpoint directory is touched.
- **Registered-behaviour test (gated: CUDA, corpus, output root):** `offline_baselines._run_train` regenerates
  `output/p4_4/checkpoints/iql_seed101.pt`, the registered P4.4 path with defaults and the seeds narrowed to 101 by
  monkeypatch, on CUDA with one torch thread. It is compared tensor for tensor (`torch.equal` on every key of `model`, and
  the canonical digest `b2725a29…` read from the file). If equality fails, the first differing tensor is reported. It is
  never loosened.
- **Mutants run and pasted:**
  - M1: `eval()` → `train()` (the brief's);
  - M2: the advantage reuses `v_pred.detach()` under `"off"`;
  - M3: the separate V forward placed after the V step;
  - M4: no return to `train()` after `value(s')`;
  - M5: default flipped to `"off"`.
