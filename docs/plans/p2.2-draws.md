## 2. Rulings from the coordinator (2026-08-06) that this plan implements

1. **Layout under `scenarios/draws/`**, with one added line in `.gitignore` (not a frozen file; direct
   edit authorised). `datasets/draws/` is **rejected**: P2.4's linter scans `datasets/` as corpora and
   demand files are not corpora. **The tool must refuse to write outside its `out_root`.**
2. **Pin the canonical draw definition by constant, never by value** — import `DEFAULT_BASE_SEED`,
   `DEFAULT_THIN_P`, `DEFAULT_JITTER_SIGMA_S`, `DEFAULT_VOLUME_SCALE` from `flow_randomizer` and record
   all four in provenance. (Context recorded by the coordinator: `collect.py --base-seed` is overloaded
   three ways — randomiser seed, MAPPO agent seed, per-episode engine seed — so draw identity is
   currently coupled to unrelated seeding. Realigning `collect.py` is a **follow-up, not this task**.)
3. **Materialise draw 0**, labelled nominal.
4. **No `.sumocfg`** — P7.3 owns it. Provenance must record that a rendered hangzhou `routes.rou.xml`
   inherits the **unbound `<vType>`**, so these files must not feed a transfer measurement until P7.0's
   parity contract lands (`BRIEF_04 §3`).
5. **Reuse `collect.py`'s path-resolution logic** rather than reimplementing the `dir + flowFile` trick;
   a second independent implementation is exactly how two subtly different draw paths appear.
6. **Load-bearing divergence test must run on hz1x1 or grid4x4, never cologne3.** Measured over 5 seeds
   (coordinator, 2026-08-06): hz1x1 σ=0.0000, grid4x4 σ=0.0000, **cologne3 σ=3.3239** — on cologne3 two
   runs of the *same* draw already differ, so a divergence assertion there would pass for the wrong
   reason.

## 3. Output layout

```
scenarios/draws/<scenario_key>/draw_<NNNN>/
    flow.json          # drawn CityFlow demand, source formatting preserved byte-for-byte
    cityflow.json      # sim config: source config with dir/flowFile repointed at this draw
    routes.rou.xml     # SUMO rendering; ONLY where the .sumocfg names an existing template
    provenance.json    # full provenance record (§5)
```

- `<scenario_key>` = **the stem of the source sim config** (`cityflow1x1`, `cityflow_grid4x4`,
  `cityflow_cologne3`). Identical to the `scenario_id` `collect.py` already writes into every manifest
  (`offline/collect.py:518-523`), so no new registry exists that could drift out of sync with it.
- `draw_<NNNN>` is `f"draw_{draw_id:04d}"`: zero-padded so lexical order equals numeric order for the
  whole registered range (0, 1-999 training, 1000-1099 held out), and a deterministic function of the id.
- The draw id is in the **path**, so a config cannot be silently confused with another draw, and
  `grep -r draw_1000 scenarios/draws` enumerates a pool.

**Lookup, for the draw-cycling trainer (brief §5):** `draw_config_path(scenario_key, draw_id, out_root)`
is a pure path function — no I/O, no directory scan — so the trainer can pre-build one env per draw and
rotate them without touching the filesystem per episode.

## 4. Module — `offline/materialise_draws.py` (NEW)

Public API:

```python
DEFAULT_OUT_ROOT = Path("scenarios/draws")
TRAINING_POOL    = range(1, 1000)      # PREREGISTRATION.md §5
HELD_OUT_POOL    = range(1000, 1100)   # D4

def scenario_key_for_config(source_config) -> str
def draw_dir(scenario_key, draw_id, *, out_root=DEFAULT_OUT_ROOT) -> Path
def draw_config_path(scenario_key, draw_id, *, out_root=DEFAULT_OUT_ROOT) -> Path
def classify_draw_pool(draw_id) -> str        # "nominal" | "training" | "held_out" | "unregistered"
def load_provenance(scenario_key, draw_id, *, out_root=DEFAULT_OUT_ROOT) -> dict
def materialise(source_config, draw_ids, *, out_root=DEFAULT_OUT_ROOT, force=False,
                dry_run=False) -> list[MaterialisedDraw]
def main(argv=None) -> int                    # CLI
```

`MaterialisedDraw` is a frozen dataclass: `scenario_key`, `draw_id`, `pool`, `directory`,
`config_path`, `flow_path`, `sumo_path | None`, `n_vehicles`, `flow_sha256`, `action` ∈
{`"written"`, `"kept"`, `"replaced"`, `"planned"`}.

Randomiser construction is **not parameterised on the CLI**: `FlowRandomizer(source, base_seed=
DEFAULT_BASE_SEED, jitter_sigma_s=DEFAULT_JITTER_SIGMA_S, thin_p=DEFAULT_THIN_P, volume_scale=
DEFAULT_VOLUME_SCALE)`, imported as constants per ruling 2. A flag here would let two callers create
two different demands under the same draw id — the exact defect the ruling closes.

CLI:

```bash
.venv/bin/python -m offline.materialise_draws \
  --env-config configs/sim/cityflow1x1.json \
  --env-config configs/sim/cityflow_grid4x4.json \
  --env-config configs/sim/cityflow_cologne3.json \
  --draws 0 1 2 3 4 5 --draws-range 1000 1005 \
  [--out-root scenarios/draws] [--force] [--dry-run]
```

`--draws-range` is half-open `[START, END)`, matching `collect.py:318-325` so the two CLIs cannot mean
different things by the same flag.

### Reuse, not reimplementation (ruling 5)

`_cityflow_flow_source` and `_write_draw_config` are imported from `offline.collect` at module level.
Consequences accepted and documented in the module docstring:

- importing `offline.materialise_draws` pulls torch (via `collect` → `agent.utils.utils`);
- `dir` in a written config is **absolute**, because that is what the engine-verified helper produces.
  The tree is git-ignored and machine-local, so absoluteness costs nothing and removes the CWD
  dependence that `configs/sim/*.json` has;
- `_write_draw_config` computes `flowFile` as a relpath from the scenario dir to `Path(drawn_flow)
  .resolve()`. It is therefore called with the **final** flow path while writing into the staging
  directory — otherwise the relpath would point at the staging location and break after the rename.
  A test pins exactly this (§6, T6).

## 5. Provenance record (`provenance.json`, `format_version = "materialised-draw/1.0"`)

```
format_version, scenario_key, draw_id, pool, is_nominal_control,
source_config, source_config_sha256, source_flow, source_flow_sha256,
source_roadnet, source_roadnet_sha256,          # topology is NOT perturbed; proven by digest
randomizer = {base_seed, jitter_sigma_s, thin_p, volume_scale},   # from the flow_randomizer constants
draw = {seed, n_vehicles, source_sha256, params},                  # the FlowDraw, applied params
files = {flow.json: sha256, cityflow.json: sha256, routes.rou.xml: sha256 | absent},
sumo = null | {template_rou, depart_offset, sumocfg, vtype_bound: bool, caveat: str},
sumo_skipped_reason = null | str,
numpy_version, git_commit, git_dirty
```

Two deliberate choices:

- **No wall-clock timestamp.** A materialised draw is a deterministic function of its inputs, so
  omitting the clock makes "this re-run was a no-op" checkable by **byte equality** of
  `provenance.json`. A timestamp would make every re-run look like a change.
- `numpy_version` is recorded because NEP 19 gives `np.random.Generator` no cross-version stream
  guarantee — the same reasoning `collect.py:546-552` records for `flow_draw_sha256`.

`vtype_bound=false` plus the caveat string carries ruling 4: hangzhou's template defines
`<vType id="pkw">` and never references it, so a rendered file reproduces that gap faithfully and
**must not feed a transfer measurement until P7.0's parity contract lands (BRIEF_04 §3)**.

## 6. Filesystem-mutation barrier — three ordered phases

**Phase 1 — validation only. No `mkdir`, no write, no delete.**
Source config, flow, roadnet exist and parse · draw ids are `>= 0` and unique · `scenario_key` matches
`^[A-Za-z0-9._-]+$` and is neither `.` nor `..` · **every planned output path resolves inside
`out_root`** (ruling 1) · for each already-existing draw dir: it is complete and its digests and
provenance match what we would write (→ `kept`), or it conflicts (→ refuse unless `--force`).

**Phase 2 — build everything in memory.** Entries, rendered CityFlow bytes, rendered SUMO bytes, the
provenance dict, all digests. Total for the 3 headline scenarios × 11 draws is ≈30 MB of bytes; the
files themselves are ≤1.5 MB each. Any error here still leaves the tree untouched.

**Phase 3 — stage, then commit.** Write into `<out_root>/.staging-<pid>-<n>/`, then `os.replace` each
staged directory into place (same filesystem → atomic rename), recording completed renames so a failure
mid-commit rolls back the ones already done. `--force` replacement moves the old directory aside first
and unlinks it only after the new one is in place — never a delete before a successful write. The
staging root is removed in a `finally`, so a failed run also leaves **no new directories**.

`--dry-run` stops after phase 1 and returns `planned` records, writing nothing.

## 10. Known limitations, declared up front

- A written `cityflow.json` embeds an **absolute** `dir`, so the tree is machine-local. It is
  regenerable byte-for-byte from the provenance, and it is git-ignored, so this is a property rather
  than a defect — but a moved checkout must re-materialise.
- Draw identity is `(base_seed, draw_id)`. This tool pins `base_seed` to the module constant; anything
  that re-draws with a different base seed (today: `collect.py --base-seed`, default 0) produces a
  *different* demand under the same id. Out of scope here per ruling 2, and carried into the Return
  Packet as the follow-up it is.
- SUMO files are rendered but **not runnable** without a `.sumocfg` (P7.3) and must not feed a transfer
  measurement before P7.0's parity contract (BRIEF_04 §3).
