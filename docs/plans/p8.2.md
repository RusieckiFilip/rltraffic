The episode loop mirrors `offline/horizon_metric.horizon_rollout` line for line in its order (`info = env.reset(seed=1000)`; for
`max_steps` decisions: decide → `env.step`), **minus every accumulation**. The reward is received and discarded, no
`average_travel_time` sample is read, and no `info` field reaches the record. **Only the decision call sits inside the timer.** The
diagnostic wrappers of `transfer_curve` (RTG and reward series) are evaluation instrumentation and are NOT in the timed call.

### 5.2 The numbers
- **Clock:** `time.perf_counter_ns()` immediately before and after the decision call. On CUDA, `torch.cuda.synchronize()` before
  BOTH readings (the sync function is injected, so T-timer can spy on it).
- **W = 20** decisions of each episode are warm-up, excluded from the statistics by count, and recorded. That is ≥ 20 for the DT,
  whose window is full from decision index 19 at K = 20, and uniform for every row.
- **N = 3** episodes per (row, device), one per held-out draw **1000, 1001, 1002** (brief; F10/Q8), engine seed 1000 (`reset(seed=1000)`,
  the evaluations' engine seed). Each episode has exactly 360 decisions (V8, asserted), so **3 × (360 − 20) = 1,020 timed decisions ≥
  1,000** per (row, device). The record refuses to be written if any episode has a count other than 360.
- **Devices:** CPU (primary) and CUDA for every row with a torch model. MaxPressure, fixed-time and random: CPU only, CUDA recorded
  as *"not applicable: no tensor computation"* (Q12).
- **Seed:** one representative checkpoint per row (seed 101, Appendix A); the other seeds are architecture-identical (V2; asserted
  by the table builder). → Q13.
- **Statistics:** median = `numpy.median` over the 1,020 pooled timed values; **p95 = `numpy.percentile(x, 95, method="inverted_cdf")`**,
  the nearest-rank value (an observed value: the smallest x with at least 95 % of observations ≤ x). Its second route is
  `sorted(x)[ceil(0.95·n) − 1]`, exact under `==` (Q11). Milliseconds = ns / 10⁶. **Per intersection** = the whole-decision
  statistic ÷ the intersection count (1 or 16): derived and labelled, not a separate timing.

### 5.3 The regime
- **CPU (primary):** `OMP_NUM_THREADS=1` and `MKL_NUM_THREADS=1` set in the process environment BEFORE torch is imported (by the
  driver), `torch.set_num_threads(1)`, `CUBLAS_WORKSPACE_CONFIG` unset. The harness **refuses** (T-regime) unless
  `torch.get_num_threads() == 1`, both variables are `"1"` and `CUBLAS_WORKSPACE_CONFIG` is absent. **CUDA rows run in the same
  process regime**, so the two devices differ in the device alone.
- **Recorded per run and per row:** CPU model (`/proc/cpuinfo` `model name`), logical CPU count, GPU name and driver
  (`nvidia-smi --query-gpu=name,driver_version`), torch/CUDA/numpy/Python versions, `torch.get_num_threads()` and
  `get_num_interop_threads()`, the three environment variables, `/proc/loadavg` before and after each row and the run, git commit and
  dirty flag.
- **Canary:** `PROJECT_PLAN` §7's, through the existing `transfer_calibration.canary_seconds()` (`rtg_calibration.run_probe` on
  `cityflow1x1` draw 0 with `p4_3_probe.json`'s settings; it returns the seconds and the facts, `offline/transfer_calibration.py:2209-2238`),
  refusing above `transfer_calibration.CANARY_MAX_SECONDS` (2.0 s) and unless `transfer_calibration.check_canary(facts)` passes
  under `==`. It runs once
  before the first timing and once after the last. Its record (`canary_open.json`, `canary_close.json`) carries the seconds, the
  threshold, the verdict and `reproduced: true`, **not** the observed return and ATT (equal to the committed constants by
  construction when `reproduced` is true). That keeps every file of the run free of a metric value (Q9). The existing CLI
  (`python -m offline.transfer_calibration … canary`) prints the observed values in its canary line, so the harness calls
  `canary_seconds()` and `check_canary` in-process instead of capturing that line, and discards the facts once checked. Mains
  power and a
  performance plan cannot be seen from the guest; the author confirms them at the start (§7's second clause), and the packet
  records his statement.
- **Sequential:** one process per (row, device), launched one after another by the driver (`subprocess.run`, never a pool). Order:
  Appendix A's row order, each row CPU then CUDA.
- **No rate is estimated here.** The G1 pre-flight times two rows (one hz1x1 DT, one grid4x4 spatial DT) with a canary, and the
  run's schedule is derived from that.

### 5.4 Output (`p8.2-latency/1.0`)
`output/p8_2/latency/<UTC stamp>/<row>_<device>.json`, created exclusively (refuses an existing path), one per (row, device). It holds:
the row id, scenario, device; the checkpoint path and its sha256, recomputed before loading and compared with Appendix A's constant;
the factory's qualified name and the prompt with its source; draws, engine seed, W, `max_steps`; per episode the 360 integer
nanosecond values; `n_timed`, `median_ns`, `p95_ns`; the regime and machine blocks; load before and after; git provenance. **No key
names a metric** (T-no-outcome). Then `canary_open.json`, `canary_close.json` and a run record with the stamp, the row order and
`COMPLETE`/`FAILED`. Finally `output/SHA256SUMS_p8_2.txt` over `output/p8_2/`, written once after `COMPLETE` and re-verified.
