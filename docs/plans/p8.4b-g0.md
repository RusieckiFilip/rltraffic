## 1. What this task is, and its one narrow hole

`docs/reviews/T1-metric-ground-truth.md` (FAIL, 4 blockers) established that `metrics/cityflow.py`'s
`average_travel_time` and CityFlow's own `Engine::getAverageTravelTime` are different quantities.
A11 registered **RULE R**: which definition the paper's claims rest on is decided per scenario by an
**ENGINE-SEMANTICS GATE** with four criteria. This task builds that gate's instrument and runs it on
`hz1x1` and `grid4x4`.

The hole is narrow and named: `offline/admission_probe.py:558` obtains `att_engine` by calling
`env._eng.get_average_travel_time()` directly, and **nothing in this repo checks what that number
means on any network.** T1 checked it on hz1x1 with a script that lived in `/tmp` and no longer exists.

**This task reports measurements. It issues no verdict on which metric is primary** (BRIEF_32 §6).

## 3. The reconstruction, derived rather than assumed

### 3.1 Snapshot grid

Define `snapshot(t)` = the engine's vehicle-id sets observed while `engine.step == t`, i.e. at
`getCurrentTime() == t · interval`. The observer takes one **immediately after each `next_step()`**,
so it collects `t = 1 … S` where `S = max_steps × delta_time`. `snapshot(0)` is not needed:
`Engine::reset` clears `vehiclePool` (`engine.cpp:744-757`), so it is empty.

### 3.2 The alignment, from §2.1

Let a vehicle `v` be created by `Flow::nextStep` during the call that takes `step: k → k+1`.
At that moment `getCurrentTime() == k·interval`, so **`enterTime(v) = k·interval`**, and `v` is in the
pool from then on. It is therefore absent from `snapshot(k)` and present in `snapshot(k+1)`:

```
first_seen(v) = enterTime(v) + interval                                        (A)
```

Let `v` be erased during the call `m → m+1`. The engine credits
`cumulativeTravelTime += m·interval − enterTime(v)` at a moment when `getCurrentTime() == m·interval`.
`v` is present in `snapshot(m)` and absent from `snapshot(m+1)`, so `last_seen(v) = m·interval` and

```
engine credit for a finished v = last_seen(v) − enterTime(v)
                               = last_seen(v) − first_seen(v) + interval        (B)
```

For `v` still in the pool at the final snapshot `S`, the engine contributes
`S·interval − enterTime(v)`, and `last_seen(v) = S·interval`, so the **same expression** applies.

```
contribution(v) = last_seen(v) − first_seen(v) + interval,  for EVERY v          (C)
ATT_reference   = Σ contribution(v) / |{v ever seen}|
```

**(C) is the brief's §4 two-branch formula with `T := last_snapshot_time + interval`,** and
**Amendment A6 approves the collapse to the single expression**, with criterion 1 as the arbiter.

### 3.3 The entered-only variants — TWO of them, and Q7 is which one (3a) scores

BRIEF_32 §4 defines the entered-only variant as *"identical except that it observes
`get_vehicles(include_waiting=False)` and admits a vehicle at the first second it is running"*. Call
that **`W_running`**: population = vehicles that ever ran, clock starts at ADMISSION.

A12 (3a) justifies bit-identity at `never_entered == 0` by *"the two populations are the same set of
vehicles"*. That argument is about the POPULATION only, and it is satisfied by a second variant:
**`W_population`** — population = vehicles that ever ran, clock starts at POOL ENTRY (the engine's own
`enterTime`), i.e. `first_seen`/`last_seen` taken from the `include_waiting=True` stream and the id set
taken from the `include_waiting=False` stream.

**Both are computed, both are reported, on every episode.** §8 is the question of which one (3a) is
scored against; the measurement does not depend on the answer.

### 3.4 The metric-cadence reconstruction — A12 (3c), REQUIRED, REPORTED, NOT GATING

A third reconstruction replays `metrics/cityflow.py`'s algorithm (§2.3) over the **decision-grid
subset** of the running-population snapshots (`t % delta_time == 0`), from a fresh `prev_active =
set()`. It imports nothing from `metrics/`: it is an independent implementation of the published
algorithm, which is what makes its agreement with `att_ours` evidence rather than a tautology.

### 3.5 Denominator

`|{v ever seen in an include_waiting=True snapshot}|`. Vehicles deleted by `planRoute` for an invalid
route are created and destroyed inside one `nextStep`, so they appear in no snapshot **and** are never
credited to `finishedVehicleCnt` — the two sides stay consistent. Criterion 2 re-checks it per episode
against `admission_probe.read_admission_at_horizon` invoked **live** (Amendment A1).

## 4. Module design

### 4.1 A11's independence requirement, and how it is honoured mechanically

A11: *"an independent reconstruction of the engine's quantity … importing nothing from `metrics/` and
nothing from `offline/admission_probe.py`."* **Amendment A3 adopts the split**: the constraint binds
the RECONSTRUCTION; the HARNESS may import both, because criteria 2 and 3 are *defined* as comparisons
against the probe.

* **Layer A — the reconstruction.** The observer env, the window bookkeeping, the four arithmetic
  reconstructions. Imports: stdlib, `numpy`, `envs.cityflow_env`, `experiments.envs.phase_control_cls`.
  **No `metrics`, no `offline.admission_probe`, in any function body.**
* **Layer B — the gate harness.** Episode selection, policy factories, the criteria, the artifact.
  Imports `offline.admission_probe`, `offline.dt_gate`, `offline.horizon_metric`,
  `offline.method_tier_grid`, `offline.materialise_draws`, `offline.tier_sweep`.

**Enforced by `test_the_reconstruction_imports_neither_metrics_nor_the_admission_probe`:** an AST walk
over the module that, for every function/class named in `RECONSTRUCTION_SURFACE`, asserts no
`Import`/`ImportFrom` of `metrics*` or `offline.admission_probe` and no attribute chain resolving to
either. It ships a positive control and asserts the allowlist is non-empty.

⚠️ **Disclosed rather than hidden:** the subclass inherits `CityFlowEnv._create_metrics`
(`envs/cityflow_env.py:232-241`), which constructs `metrics.CityFlowMetrics`. That is the *env's*
behaviour and is required for `att_ours` to exist at all; **the reconstruction's arithmetic never reads
the metrics object.** The module docstring states this explicitly.

### 4.2 The observer

```python
class PerSecondEngineObserver(CityFlowEnv):
    def reset(self, *, seed=None, options=None): ...     # clears observer state, then super()
    def _simulate(self, num_steps: int) -> None:
        for _ in range(num_steps):
            self._eng.next_step()
            self._observe()                              # one snapshot per engine step
```

`_observe()` records, per vehicle id, `first_seen`/`last_seen` on the pool population and on the
admitted population, and stores the full admitted **set** only at decision-grid times (`t %
delta_time == 0`) for §3.4. Times are the engine's own `get_current_time()`, read once per step, so a
mismatch between our model of `step` and the engine's would surface rather than be assumed away.

Measured cost this session (pilot, §8.1): **0.7 s** per hz1x1 episode and **1.4 s** per grid4x4
episode end to end, so the whole campaign is ~1 minute.

### 8.2 The falsification

**A12 (3a):** *"on every episode where `never_entered == 0` the engine-population reconstruction and
the entered-only reconstruction must be BIT-IDENTICAL … Zero tolerance."*

Row 4 above has `never_entered == 0` and `P − W_running = 0.070295 ≠ 0`. Row 1 has
`never_entered == 0` and `P − W_running = 0.670160 ≠ 0`. **Under BRIEF_32 §4's definition of the
entered-only variant, (3a) FAILS.**

### 8.3 The root cause, measured as an IDENTITY rather than argued

A12's justification is *"the two populations are the same set of vehicles"*. That is true of the
POPULATIONS and false of the CONTRIBUTIONS. `never_entered == 0` says no vehicle is **still** waiting
at the horizon; it does **not** say no vehicle **ever** waited. A vehicle that sits in a lane's
insertion buffer for `d` seconds and then enters is in both populations, but the engine's clock starts
at `enterTime` (pool entry) and the entered-only clock starts at admission — so it contributes `d` less.

Measured on hz1x1 maxpressure draw 1000, all four quantities from the same run:

* `last_seen` from the admitted stream differs from `last_seen` from the pool stream on **0 of 1813**
  vehicles — as §2.1's `setRunning` finding predicts, so the whole difference is on the *first* seen.
* admission latency `first_run[v] − first_pool[v]`: mean **0.6701599558742416 s**, max **11.0 s**,
  **465 of 1813** vehicles non-zero.
* `W_running − E = −0.6701599558742544`, against `−mean_latency = −0.6701599558742416`.
  **The two agree to 1.3e-14, i.e. they are the same quantity summed in two different orders.**

So, with `never_entered == 0`:
```
W_running − P  ==  − mean_over_created( first_run[v] − first_pool[v] )
```
(3a) as written therefore demands that **every vehicle be admitted on the same engine step it is
created**, which is a property of the *traffic*, not of the instrument.

Row 4 is the clincher and it points at the fix: **`W_population − E = 0.000000` exactly** on that
episode — the population-only variant IS bit-identical when `never_entered == 0`, which is precisely
what A12's justifying sentence describes.

### 8.4 What I propose, and it is the coordinator's choice

Both variants are computed and reported on every episode under every option, so **no option changes a
single measured number**; the choice is only what (3a) is *scored* against.

| option | (3a) is scored on | consequence |
|---|---|---|
| **(a)** as literally registered | `W_running` | (3a) **FAILS on both scenarios**, and A11's FAIL branch fires — for a specification defect, which is the exact outcome A12 was written to prevent |
| **(b)** amend (3a) to name `W_population` | `W_population` | matches A12's own justifying sentence; (3a) stays an EXACT, zero-tolerance identity and still fails if the population selection is wrong; needs an A13 |
| **(c)** keep `W_running` and re-scope (3a)'s condition | `W_running`, on episodes where `never_entered == 0` **and** mean admission latency `== 0` | preserves the letter but the qualifying set may be empty, so the control could report nothing |

**My recommendation is (b).** It is what A12's stated reasoning describes, it keeps the zero tolerance
that A12 explicitly advertises as a *tightening*, and it leaves `W_running` — our metric's actual
population *and* clock — reported on every episode as the quantity that feeds `Rule R`.
⚠️ **I do not implement a choice.** I implement the measurement, report (3a) under **both** readings
with observed values, and mark the criterion's outcome as pending the ruling.
