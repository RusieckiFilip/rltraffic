## Context

The July "`--workers > 1` falls over" report was misdiagnosed as a fork/spawn deadlock. The 2026-07-28
re-investigation (`docs/notes/P0.3_spawn_attempt.md`) refuted that and measured the real cause: torch's
default intra-op pool takes one thread per core, so N worker processes ask for 16N threads on 16 cores.

| workers | unpinned | pinned (`OMP=MKL=OPENBLAS=1`) |
|---:|---:|---:|
| 1 | 339.7 s | **247.7 s** (1.37x) |
| 3 | 1165.3 s | 76.3 s (4.45x) |
| 6 | >=1200 s | **58.6 s** (5.80x) |

> **Annotation 2026-08-03 (P0.5):** the (1.37x / 4.45x / 5.80x) ratios in the table above are **retired
> cross-session arithmetic** (pinned wall over an unpinned baseline from a different day-state, banned by
> the Decisions Log). Left unchanged as a dated record. The trustworthy single-session figure is
> 199.2 s -> 50.2 s (~3.97x at workers=6); the corrected justification lives in `experiments/runner.py`'s
> docstring and `docs/patches/runner_liveness_docs.patch`.

The shipped parallel path is therefore a *regression* (workers=3 is 3.4x slower than sequential), and
pinning helps even at workers=1 because these MLPs are far too small to pay for a thread pool. The payoff
is the P5 online-baseline budget: ~15-60 h sequential becomes ~3-10 h. The note left the fix as an open
question precisely because it lands in a frozen file; this brief is the authorisation to apply it.

**Re-verified before planning** (scratchpad probe, `.venv/bin/python`, 16 cores, torch 2.11.0+cu128):

```
parent pid 1505920 threads 16
child unpinned: [(1505955, 16), (1505956, 16)]     <- forked children inherit 16
child pinned:   [(1505959, 1), (1505960, 1)]       <- set_num_threads(1) in the child works,
parent after: 16                                       even after the parent ran a real torch op
```

## The change

`experiments/runner.py` only: a documented constant and helper near the top, and one call inside
`run_cell`.

```python
CELL_TORCH_THREADS: int = 1          # + comment block carrying the table above

def limit_torch_threads(n_threads: int = CELL_TORCH_THREADS) -> int:
    """Pin torch's intra-op pool for the calling process; return the count in effect."""
    import torch
    torch.set_num_threads(int(n_threads))
    return int(torch.get_num_threads())   # read back, not the requested value
```

and inside `run_cell`, immediately after the `backend_ready` early-return: `limit_torch_threads()`.

### Why option (a), `set_num_threads` in `run_cell`

`run_cell` is the unit of work on *both* paths: one process per cell under `ProcessPoolExecutor`, and
the main process when `workers=1`. One call site therefore buys both the 5.80x parallel win and the
1.37x sequential win.

- **(b) `ProcessPoolExecutor(initializer=...)`** reaches only `workers>1`, leaving the sequential gain
  to a second mechanism in a second place.
- **(c) env vars before pool creation** does work here (torch enters lazily via `build_agent`, so nothing
  has imported it at fork time), but it mutates `os.environ` process-globally and stops working silently
  the day anything imports torch earlier. That failure mode surfaces as a slow run, not an error, which
  is exactly the class of bug this repo's rules exist to prevent.

**Local `import torch`, never module-level.** `experiments/` has no module-level torch import (verified:
`grep -rn torch experiments/` matches only two comments), which is what keeps `--dry-run` instant and
turns a missing backend into a `skipped` cell instead of a crash. The brief forbids adding one. Placing
the call *after* the skip check additionally means a backend-less cell never pays for the import.

**Deliberate side effect:** on the sequential path this pins the caller's own process. That is precisely
what the 1.37x row asks for; it is stated in the docstring rather than hidden.

## Tests — `tests/test_runner_threading.py`

Written and run RED before the patch is applied. An `autouse` fixture saves and restores
`torch.get_num_threads()` around every test in the file, so the file is order-independent under
`pytest-randomly`. Each test first forces the parent process to **2** threads, so no assertion can pass
vacuously by inheriting an already-pinned parent — a real hazard, because after this change every
existing `run_matrix(workers=1)` test pins the pytest process to 1.

| # | Test | Proves |
|---|---|---|
| T1 | Module-level probe submitted through `ProcessPoolExecutor(max_workers=2)`; the probe calls `runner.limit_torch_threads()` and then **independently re-reads** `torch.get_num_threads()`, returning `(os.getpid(), threads)`. Parent asserts `pid != os.getpid()` and `threads == 1`. | The property, measured **in the child** and returned to the parent (brief test 1) |
| T2 | Real `run_matrix(config, workers=2)` over the `FakeEnv` imported from `tests/test_experiments_runner_smoke.py`; `runner.make_env` is monkeypatched to a module-level recorder (bound with `functools.partial`, inherited by the fork) that appends its observed thread count to `tmp_path/threads_<pid>.txt`. Parent asserts >=1 file, every recorded value `1`, every pid != parent, and cells `ok`. | `run_cell` actually applies the pin on the shipped pool path, not just the helper in isolation |
| T3 | `run_matrix(config, workers=1)` -> cell `status == "ok"` with the expected policies, **and** the calling process sits at 1 thread afterwards. | Sequential path still correct *and* pinned (brief test 2) |

T2 skips with an explicit reason if the start method is not `fork`, because the parent-side monkeypatch
only reaches the child under fork. `FakeEnv` and `_smoke_config` are imported from the existing smoke
test rather than reimplemented.

4. **`torch.set_num_threads()` pins torch's pool only**; the original benchmark also pinned MKL/OpenBLAS,
   which numpy uses. The runner's numpy work is trivial (means over short lists), so no gap is expected —
   but if the re-measurement misses ~247 s / ~59 s materially, the shortfall is reported and (c) is
   proposed as a follow-up rather than this change being silently widened.
