## 1. E1.3 — two test-strength fixes and one driver flag

### 1.1 `test_the_canary_stage_exits_non_zero_on_a_mismatch` (MC8 must die)

Today it asserts `"canary" in out and "-1.0" in out`. `main`'s refusal handler prints
`transfer_calibration: canary local_return -1.0 != …`, which satisfies both substrings, so moving
`check_canary` **before** the print leaves the test green. The assertion is satisfied by prose.

Replacement assertion, on **structure and position**:

* split stdout into lines;
* `lines[0]` must start with `"canary "`;
* `lines[0]` must carry the four fact names, and — because E1.4 makes the facts JSON — the tail of
  `lines[0]` after `" s "` must **parse as a JSON object** carrying `two_routes_agree`;
* the refusal line (`transfer_calibration:`) must exist at an index **strictly greater than 0**.

The refusal message for a `local_return` mismatch contains neither `two_routes_agree` nor a JSON
object, so under MC8 line 0 becomes the refusal and every one of those assertions fails.

### 1.2 `test_the_driver_gates_on_the_canary_before_consuming_the_token` (MD2 must die)

Today: `assert "tee /dev/stderr" in text`. The driver's own **comment** contains that string, so
deleting `tee` from the code line leaves the test green.

Replacement: a module-level helper `_driver_code_text()` that drops every line whose first
non-blank character is `#`, and assert `"canary | tee -a /dev/stderr)" in _driver_code_text()` —
the code line with its closing parenthesis, searched only over code.

Also added here (E1.4 item 1's "nothing before the token"): the `record-canary` invocation must
appear **after** `rm -f "$TOKEN"` in the driver text.

### 1.3 Driver: `tee /dev/stderr` → `tee -a /dev/stderr`

With the hazard as the comment's stated reason: `tee` opens `/dev/stderr` with `O_TRUNC`, so when an
operator runs the driver with `>> log 2>&1` the second write resets the file offset and destroys
everything already in the log. Observed in `/tmp/p72b_run3.log` (now
`output/p7_2b_runs/tmp_capture_p72b_run3.log`), whose header is cut through the canary line.

## 2. E1.4 — this run's canary reaches the artifact from a manifested file

### 2.1 The defect, restated from the artifact

`report` builds the canary block from the **probe chunks**' `canary_seconds`. Run 1 rolled the
chunks; runs 2, 3 (and 4) reuse them by content. So the block reads `0.89` — run 1's canary — while
the run that wrote the artifact measured `0.79`, and it prints `checked_against` beside it, implying
run 1's canary was checked against the references. Run 1's canary *was* observed (recovered from
`output/p7_2b_runs/tmp_capture_p72b_run.log`) but was never *checked* by any code: `check_canary`
did not exist until `8e70d77`.

### 2.2 New module surface in `offline/transfer_calibration.py`

| name | what |
|---|---|
| `CANARY_RECORD_NAME = "canary.json"` | the file name, one literal |
| `format_canary_line(seconds, facts) -> str` | `canary <s:.2f> s <json.dumps(facts, sort_keys=True)>` |
| `parse_canary_line(line) -> tuple[float, dict]` | the inverse; raises `ValueError` on anything that is not exactly that shape |
| `record_canary(line, *, work_dir) -> Path` | parse, then `_write_json` the record with `_git_provenance()` |

`canary.json` payload:

```json
{"format_version": "p7.2b-calibration/1.0",
 "line": "<the exact line the driver captured>",
 "seconds": 0.79,
 "facts": {"att_horizon": …, "decisions": 360, "local_return": …, "two_routes_agree": true},
 "threshold_seconds": 2.0,
 "git_commit": "…", "git_dirty": false}
```

`record_canary` deliberately **does not** call `check_canary`. Its job is to preserve what the driver
observed, including a mismatch — that is E1.2's whole point, and `report` is the checker (item 2).
The driver can never reach `record-canary` with a failing canary anyway: the canary stage exits
non-zero first and `set -euo pipefail` aborts before the token.

`parse_canary_line` refuses: a line without the `canary ` prefix; a missing ` s ` separator; a
non-float seconds field; a facts field that is not JSON; JSON that is not an object; an object
missing any of the four fact names. It parses **before** anything is written (filesystem barrier).

`canary_seconds()` is unchanged. Its facts are already plain Python types — verified by reading the
construction chain: `episode_return_two_routes` appends `float(payload["reward"])`,
`run_probe` sets `att_horizon = samples[-1]` where `samples.append(float(...))` and
`decisions = len(post_step)`; `two_routes_agree` is `float == float` → `bool`. numpy is 2.5.1 in
this venv, whose repr of a `float64` inside a dict would be `np.float64(…)`, and run 3's
`canary.log` shows `-32648.0`. So `json.dumps` cannot fail on them.

### 2.3 CLI

`record-canary --line "<line>"` → `record_canary(args.line, work_dir=args.work_dir)`; prints the path
it wrote; exit 0. Malformed → `ValueError` → `main`'s handler → exit 1.

### 2.4 `report`

New refusals, all before any write (the barrier is already the module's shape — `_write_json` is the
last statement):

1. `work/canary.json` missing → `FileNotFoundError` naming the file and saying, in the brief's own
   terms, that from this commit on a work directory without it is not a run.
2. `check_canary(record["facts"])` re-run on the record → `ValueError` if it fails. A chunk's
   self-claim is not evidence.
3. the probe chunks must agree on `git_commit` → `ValueError` if they do not (item 3).

New canary block. The block's **own top level is the this-run record** — which is what item 4 means
by "the top-level `seconds` / `verdict` describe the run that wrote the artifact" — and the chunks'
canary is one clearly named sub-block beside it:

```json
"canary": {
  "seconds": 0.79, "threshold_seconds": 2.0, "verdict": "at speed",
  "observed": {…the four facts from canary.json…},
  "checked_against": {…the references…},
  "source": "output/p7_2b/canary.json …",
  "git_commit": "…", "git_dirty": false,
  "recipe": "…",
  "probe_chunks_canary": {"seconds": 0.89, "git_commit": "f31973eb…",
                          "correctness_half": "not recorded in these chunks"}
}
```

`checked_against` therefore occurs **exactly once** in the serialised artifact, beside the observed
facts it was checked against (item 4). No `re_checked_by_report: true` flag: a boolean that says
"I checked" is a self-claim that a mutation makes into a lie, whereas `observed` + `checked_against`
side by side let a reader of `docs/data/` alone **redo** the check. That is the stronger form.
