## Blocking — must be resolved before queue item 0 runs

**B1 — the harness cannot evaluate a checkpoint; it always retrains.** `rederive_anchors.py:106`
calls `_train_agent` and nothing else, although the frozen `experiments/runner.py:299-349` exposes a
`from_checkpoint` / `_load_agent` path and the MAPPO@1000 checkpoints exist on disk. P8.0's own
measurement puts retraining at **±5.1 %** — **twice the +2.5 % grid4x4 margin** and comparable to
cologne3's +5.8 %. *A paper reviewer would conclude: they settled a 2.5 % ordering by retraining the
policy on an instrument they had already shown perturbs the number by 5 %.*

**B2 — `final_completed` is a LAST-episode value while `final_vehicle_count` is a MEAN over
episodes, and the documented formula at `:52` mixes them.** Demonstrated: completed per episode
`[343, 349, 334]`, reader reports `334.0`; `entered` as `rederive_tier1` computes it = **488**
against an honest per-episode mean of **495.67**. Dormant only because `rederive_tier1.py:54` passes
`episodes=1`; it **arms at `eval_episodes=3`, which is the anchors' own setting.** `HorizonRollout`
exposes no `per_episode_completed` or `per_episode_vehicle_count`, so a consumer cannot repair it
without editing the reader.

**B3 — A4's mandatory co-report stops at the dataclass; the >5 % condition exists nowhere in code.**
`final_vehicle_count` is per-cell in `results.json` but **absent** from `aggregated`, `summary.csv`,
`PROVENANCE.md` and the Return Packet table; `rederive_tier1.py:58` computes `vehicle_count` and
then drops it. Grep finds no implementation of the >5 % condition. Applied by hand to the committed
anchors, **5 of 6 pairwise comparisons are INVALID under A4 as written** — and the one that reads
"valid" is manufactured by aggregating before applying the condition (per-seed 206/99/166 vs
157.3/156.0/157.7, both means landing on 157.0 by coincidence).

**B4 — A4's restated condition is not a condition anyone can pass. This is a PRE-REGISTRATION
defect, not a P8.0 defect.** `entered` is a *population size* — stable across policies on fixed
demand (measured spread 4.1 %). `vehicle_count` at the horizon is a *congestion outcome* — the very
thing a good policy drives to zero. A 5 % band on it invalidates every comparison worth making,
including every comparison C1 exists to make. **Escalated to the user as amendment A5.**

**Coordinator's ruling on where the co-report belongs: inside the reader**, per the reviewer's three
reasons — `final_vehicle_count` and `final_completed` are already computed there from the same
rollout, so any downstream re-derivation is a second measurement path (the A2 failure exactly); the
>5 % test is a property of a *pair*, so it belongs where cells aggregate, which is the same function
that currently drops the companion; and queue item 0 calls the reader directly, so a downstream-only
rule is one nobody is forced to run. **Not** in `HorizonRollout` itself — the reader's job is to emit
**per-episode** counts so any verdict is computed honestly rather than on a mean (that is B2).

asserts exact `==`. That exactness is carrying the entire test net.
