## ⚠️ 0. WHY THIS FILE IS LATE, AND WHOSE FAULT THAT IS

**A reader comparing timestamps will see an inversion, and it is real.** `P4.md`, `P4.3.md`, `P4.4.md`
and `P4.5.md` were each committed **before** their fix rounds. This one was committed **after**.

**The cause is the coordinator's, and it is a context-discipline failure of exactly the kind CLAUDE.md
§0 names.** The review ran as a background agent and returned its report **into a task notification**.
The coordinator read it there, wrote `BRIEF_18` from it the same turn, and **never wrote the report to
disk** — so for the duration of the fix round the findings existed only in a conversation, which is
the one place this project says nothing load-bearing may live. *"The repo is the memory; the context
window is scratch space."*

**Consequences, stated rather than smoothed over:**

1. The implementer worked from **`BRIEF_18`'s enumeration**, not from this report. It flagged the
   absence at the top of its own packet rather than assuming the file was elsewhere — the correct
   response, and it is the reason nothing was silently skipped.
2. **`BRIEF_18` is self-contained**, so every finding below that carries a `BRIEF_18` reference was
   addressed. Findings **without** one were not put to the implementer during the round.
3. **This file is reconstructed from the reviewer's returned report, in full and unedited in
   substance.** It is not a summary written from memory.

**The general rule this cost us, recorded in `PROJECT_PLAN` §7:** an agent's findings are not an
artifact until they are on disk. A notification is a delivery mechanism, not a record.
