# THE PRIORITY QUESTION — the hang. ANSWERED.

## The hang is NOT reachable against the committed code. The pin is what *prevents* it.

This inverts the previous reviewer's working hypothesis. The deadlock is not a fragility the change introduces or tolerates — it is a pre-existing `fork()` + libgomp hazard that `limit_torch_threads()` **eliminates**, and the mutant reintroduces by removing the pin.

**CONFIRMED — the mechanism** (`/tmp/p03rev/fork_omp2.py`; parent warms a torch OMP team, forks 2 workers, each child does 20 chained matmuls; 25 s bound):

```
exit=0  parent: torch=2  os_threads=18   RESULT MODE=pin   PARENT_N=2  OK 0.02s [(1567122, 1, 2), (1567123, 1, 2)]
exit=0  parent: torch=16 os_threads=46   RESULT MODE=pin   PARENT_N=16 OK 0.05s [(1567179, 1, 16), (1567180, 1, 16)]
exit=3  parent: torch=2  os_threads=18   RESULT MODE=nopin PARENT_N=2  HUNG 25.00s TimeoutError
exit=3  parent: torch=16 os_threads=46   RESULT MODE=nopin PARENT_N=16 HUNG 25.00s TimeoutError
```

A child that enters a parallel region with `nthreads > 1` waits forever on team threads that `fork()` never duplicated. `torch.set_num_threads(1)` before the first parallel region makes the region run serially in the master thread, so there is nothing to wait on. **Liveness, not just speed.**

**CONFIRMED — the hang reproduces only with the pin removed, and only when an earlier file warms the parent's OMP team:**

| invocation | mutant (`limit_torch_threads` neutered) | real committed code |
|---|---|---|
| `test_runner_threading.py` alone | `4 failed, 4 warnings in 2.29s` — no hang | `4 passed, 4 warnings in 2.42s` |
| smoke + **T1** only | `1 failed, 10 passed in 2.76s` — no hang | passes |
| smoke + **T2** only | **`exit=124` — HUNG, killed at 120 s** | **`exit=0`, `11 passed in 3.87s`** |
| smoke + whole threading file | **`exit=124` — HUNG, killed at 150 s** (`..........F` then silence) | `14 passed in 3.19–3.72s`, **10/10 runs** |

The trigger is precise: the smoke file must run first (it executes real torch ops in the pytest parent, warming the OMP team), **and** the child must skip the pin. T1 alone never hangs — its child does no heavy torch work; the hang lives entirely in T2, whose children run real DQN training.

**CONFIRMED — the real code does not hang under any invocation I could construct:**

That is the mutant hang, exactly as described, still alive half an hour later. I killed them. It confirms both the previous finding and the unbounded nature of a T2 hang.

## Item 3 — the vacuity risk. CONFIRMED NOT a problem.

`torch.set_num_threads` **can** raise the count after the pool has initialised, and the raise propagates to forked children:

```
initial get_num_threads: 16      after matmul: 16
after set(1): 1   after set(2): 2   after set(1) again: 1   after set(4): 4

parent after set(1)+op: 1
parent after set(2): 2
children (no pin): [(1565469, 2), (1565470, 2)]
```

So the parent forcing to 2 always takes, and no test can pass by inheritance. Confirmed live in-suite: instrumenting `pytest_runtest_setup` shows every test in the file entering at `torch_threads=16` (restored by the autouse fixture) even when the file runs first, and at 1→forced-2 when the smoke file runs first.

## Item 4 — remediation

None required for the shipped code. See finding N7 for the residual test-infrastructure risk and its cost.

**N1 — `runner.py:293` + missing packet line: the pin is load-bearing for liveness, and nothing on disk says so.**

This is the single most valuable thing this review produced and it belongs in the docstring and the packet.

**N2 — `experiments/runner.py:293`: the pin changes torch's numerical results at exactly the shape `p0_baselines` MAPPO uses.** Not mentioned in plan, packet or docstring.
