### 5.1 RESOLVED by restoring exactness, not by loosening the comparison

Ruled 2026-08-17: *"try to restore exactness before loosening anything"*, with `math.fsum` as the
preferred mechanism. **`fsum` turned out to have nothing to act on**, and establishing that was the
whole job.

**Where the ulp actually came from.** I dumped every intermediate of the Wilcoxon path as hex on both
machines (throwaway branch, run `32028372830`, since deleted). **Bit-identical on both:**

| quantity | both machines |
|---|---|
| `sum(L)`, `sum(R)` | `0x1.47fc9b708164ap+13`, `0x1.49f1a0b124b95p+13` |
| `w_plus`, `w_minus` | `0x1.0d00000000000p+10`, `0x1.f0c0000000000p+11` |
| `statistic`, `variance` | `0x1.0d00000000000p+10`, `0x1.4a6b800000000p+16` |
| `z` | `-0x1.3ebf186a61521p+2` |
| erfc **argument** | `0x1.c2c68c1f67a84p+1` |
| **`math.erfc` result** | dev `0x1.54a3046cb4c1dp-21` · runner `0x1.54a3046cb4c1cp-21` ← **the only difference** |

glibc **2.43** against **2.39**. There is **no float summation anywhere in that path** — the ranks
are half-integers and sum exactly, which I verified rather than argued (`w_plus == fsum(ranks)`, and
`ties: [1]`, so the tie correction is zero). Everything from the ranks to the erfc argument is
integer or IEEE-exact arithmetic. **The one non-deterministic step was the special function**, so the
special function is what changed.

**Which machine was right.** Computed `erfc` to 120 digits with `decimal` and Machin's π:
`6.34485457585274551150639655222548177…e-07`. Correctly rounded that is **`…746e-07`, the committed
value** — the runner's libm was the inaccurate side. So the fix restores the *right* number rather
than tolerating a wrong one.

**The fix.** `offline/dt_gate.py` gains `_erfc_deterministic`, a correctly-rounded `erfc` computed in
`decimal` (arithmetic exactly specified, hence platform-independent), and `_normal_cdf` uses it.
`offline/rtg_calibration.py` is **untouched** and its `==` still stands.

**No published number moves — measured, not asserted.** Of **365** committed p-value fields in
`docs/data/*.json`:

* **322** go through the normal approximation and record their own `z`. All 322 were recomputed
  through the new routine: **0 changed.** This is now

* **43** never touch `erfc` — they come from `hypergeometric_upper_tail` (`math.comb`, exact integer
