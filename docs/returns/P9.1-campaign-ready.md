## 3. B.3 — the stall remedy (`cbe796a`)
**The watchdog** (`offline/stall_guard.py`):
- `StallGuard` arms `faulthandler.dump_traceback_later(600, exit=True)` on the worker's stall file. That timer is a C
  thread needing no GIL, so it fires while the main thread is held inside C. This was shown with libc `sleep` called
  through `ctypes.PyDLL`, which keeps the GIL: the dump starts `Timeout (`, then exit 1.
- **Progress** is every `CityFlowEnv.reset` and `step`, re-armed at most once per 10 s, because each re-arm starts a new
  C thread. A stall is therefore detected after 590–600 s without progress.
- `install()` wraps the two methods **at runtime in the worker's process only**, for its whole life including interpreter
  exit, which is when the last engines are destroyed. `envs/cityflow_env.py` is not edited (Q15).

**Where it applies.**
- `evaluate`, `old-cells` and `p3a-references` take `--stall-dump`; no other subcommand does.
- The driver's `restarting` runs a worker with `--stall-dump` and restarts it only on exit 1 **with** the banner at the
  head of that run's own fresh stall file. An ordinary exception also exits 1, but with an empty file, and is not
  restarted.
- At most `MAX_RESTARTS=20` restarts, each logged in `$LOGS/restarts.log` with the UTC time and the dumped stack. Any
  other non-zero exit stops the stage as before, and a restart needs no new token.
- The `evaluate` and `old-cells` shards and P3a's references run under it. `collect` (B.3), `train`, the declarations
  and `d4rl` do not.

**Resume granularity.**
- Route (ii) and the old cells resume per episode (P8.4b writes one atomic file per episode).
- Route (i) and P3a resume per cell: the registered CLI writes a cell's 500 episodes once, so a cell in flight is rolled
  again. It is seeded, so the values are the same.
- Route (i)'s CLIs (`method_tier_grid`, `tier_sweep`) and P8.4b write their JSON through `dt_gate.write_json_atomic`
  (a unique `mkstemp` name, then `os.replace`), so a kill leaves at most a stray `.tmp`, never a partial file.

**One-off check, not a committed test.** Three real hz1x1 episodes of `behaviour@maxpressure` were rolled through
P8.4b's route under the installed guard:
- all three reproduced their committed `att_ours` (refused 0);
- there were 1,083 progress calls, which is 3 × (1 reset + 360 steps);
- the dump was empty and the exit was 0.

The run was made twice, with the same counts both times. The second, at `dd92a16` with the load recorded, is in
