## 5. 🔒 A test of mine was wrong. Here it is in full, with the diagnosis

**T5 failed on its first green run.** I did not adjust it until I had diagnosed why, and the
diagnosis is that **my test was wrong, not the code**.

*What it did:* compared the `(depart, route)` multisets of draw 0's generated parity routes and the
committed parity route file by reading `vehicle.get("depart")` as a **string**.

*Why that is wrong:* the depart is a time. The committed parity file inherits the shipped
`.rou.xml`'s integer strings (`"0"`, `"3"`, `"8"`); a drawn rendering carries
`flow_randomizer.render_sumo`'s two-decimal form (`"0.00"`, `"3.00"`). Measured:

```
committed parity           n= 2021 first departs (raw strings)=['0', '3', '8', '11']
draw 0 parent rendering    n= 2021 first departs (raw strings)=['0.00', '3.00', '8.00', '11.00']
float multiset equal: True | index-aligned: 2021 / 2021
```

So the demand is identical and my assertion was comparing **file formatting**.

*The change:* the comparison now goes through `conversion_audit.demand_from_route_file` — the same
extractor CAP(E) uses and the one A15(g)'s `2021/2021` verdict was made with — and it additionally
asserts, positively, that the two raw string forms **do** differ. The test is strictly stronger than
before: it now checks demand equality, order equality, the count, and the formatting difference that
motivates comparing semantically. **No assertion was removed.**

*Scope of the error:* the test file only. No shipped code changed because of it, and the artifact was
correct throughout — T3's CAP(E) check already compared floats.
