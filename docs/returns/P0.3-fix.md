## The change, and why this mechanism

`run_cell` is the unit of work on **both** paths — one process per cell under `ProcessPoolExecutor`, and
the main process when `workers=1` — so a single call site buys both the parallel win and the 1.37×
sequential win the benchmark reported. Option (b) `ProcessPoolExecutor(initializer=...)` reaches only
`workers>1`. Option (c) env vars works today (torch enters lazily via `build_agent`, so nothing has
imported it at fork time) but mutates `os.environ` process-globally and would stop working silently the
day anything imports torch earlier — surfacing as a slow run, not an error.

`import torch` is inside the function, never at module scope. Verified in this session:

```
$ .venv/bin/python -c "import sys; import experiments.runner; print('torch' in sys.modules)"
torch in sys.modules after import experiments.runner: False
CELL_TORCH_THREADS = 1
```

The call sits **after** the `backend_ready` skip check, so a cell with no backend never pays for a torch
import it will not use.

### How the tests avoid proving nothing

- The thread count is read **in the child** and carried back — via `pool.map` return value (T1) and via
  per-pid files on disk (T2). Every observation asserts `pid != os.getpid()` first.
- Each test forces the parent to **2** threads before forking, so an assertion of `== 1` cannot be
  satisfied by inheriting an already-pinned parent. This is a live hazard, not a theoretical one: after
  this change every `run_matrix(workers=1)` elsewhere in the suite pins the pytest process to 1.
- T1 re-reads `torch.get_num_threads()` independently instead of trusting `limit_torch_threads`'s own
  return value, so a helper that returned the right number without changing anything would still fail.
- An `autouse` fixture restores the parent's thread count after each test, so the file is
  order-independent.

**The production parent does not fork multi-threaded — measured, not assumed.** My first check
(`grep -c multi-threaded` over the benchmark's stderr → 0) proves nothing on its own, because
`DeprecationWarning` is hidden by default outside pytest. Re-checked with warnings forced visible:

```
parent importing only `experiments.runner`, forks 2 workers:   0 fork DeprecationWarnings
same parent + `import torch`:                                  2 fork DeprecationWarnings
```

So `import torch` in the parent is the trigger, and `experiments/runner.py` does not have it. The tests
must import torch to read `get_num_threads()`, so they run in a **strictly harsher** configuration than
the CLI ever does. Note that `threading.active_count()` stays 1 throughout — what CPython objects to is a
native thread registered with the interpreter by torch, not a Python-level `Thread`.

**One hardening applied:** `pool.map(..., timeout=60)` in T1, so a hypothetical child-side deadlock fails
the test instead of hanging the suite forever. 60 s against a ~2.5 s file cannot flake. T2 could **not**
be bounded the same way: `run_matrix` calls `future.result()` with no timeout, and `runner.py` is frozen
beyond the scope of this authorisation.

**Open questions / risks for the Master chat**
1. **`torch.set_num_threads()` pins torch only, not numpy's BLAS.** The original benchmark also exported
   `MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS`. The measured numbers came in *faster* than the env-var-pinned
   targets, so no gap showed up at this scale — but a future config with heavy numpy work in the cell
   loop could still over-subscribe. Adding option (c) on top would need a fresh authorisation.
2. **`experiments/runner.py` now diverges from `main`'s frozen copy.** Any later task that assumes the
   frozen set is untouched should be told this file has one authorised delta.
3. **SUMO/libsumo fork-safety is still unverified** (`P0.3_spawn_attempt.md` §6). This benchmark, like the
   original, only exercised CityFlow. Re-test the parallel path before relying on it in P7.
4. **The 1.71× / 6.77× speedup ratios are cross-session comparisons.** My pinned numbers are measured;
   the 339.7 s unpinned baseline they are divided by was measured on 2026-07-27 by another session. The
   absolute pinned numbers (199.2 s, 50.2 s) are the trustworthy figures.
