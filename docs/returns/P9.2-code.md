   stderr; a non-positive or non-finite timeout is refused before anything is written. `evaluate` takes `--watchdog-seconds`
   (default 600) and `--watchdog-file PATH`, opened for append — after the guard check, so a refused start opens nothing —
   and kept open for the process's life (faulthandler writes to it by descriptor from its own thread).
2. **The restart loop (B.3.2).** The driver gains a SHARD MODE, `p9_2_demand_shift.sh --run-shard i`, which each tmux window
   now runs (it needs no token and checks no tree, as the shard windows never did; it refuses stage 2 without pins and an
   index outside `0..SHARDS-1`). It runs `evaluate … --watchdog-seconds 600 --watchdog-file <the shard's log>` through `tee`
   into that same log; exit 0 ends the shard; **exit 1 with faulthandler's banner (`^Timeout \(H:MM:SS[.ffffff]\)!$`) in the
   part of the log THIS attempt wrote** (located by the log's byte size before the attempt, read whole before it is searched,
   so `grep` stopping early cannot SIGPIPE the reader) restarts it — it resumes from the records on disk, needs no token — and
   logs `SHARD i RESTART n/20 at <UTC time>: the watchdog cut a cell after 600 s; resuming from the records on disk; top frame:
   <the dump's first File line>`; after 20 restarts a further cut stops it (`SHARD i STOPPED: the watchdog cut it on 21
   attempts; the cap of 20 restarts is reached`); any other non-zero exit stops it (`SHARD i STOPPED: exit <code> without the
   watchdog's dump; not restarted`); every run ends `SHARD i EXIT: <code>`. `P92_WATCHDOG_SECONDS` and `P92_MAX_RESTARTS`
   override 600 and 20 (the tests scale both down); the window's command passes them, and `P92_PYTHON`, `STAGE`, `SHARDS`,
   `IQL_T_PINS`, explicitly, since a tmux window does not inherit the driver's environment.

## Deviations, decisions, open questions

- **D9** the restart loop is the driver's own shard mode (`--run-shard i`), not a separate script: it stays in "its driver"
  (B.3) and can be tested without tmux; the tmux windows run it.
- **D10** a restart needs exit 1 AND the banner in this attempt's part of the log (B.3: "exits with the watchdog's dump in its
  log"; P9.1's convention). An ordinary exception also exits 1, with no banner, and is not restarted — test (b).
- **D11** the dump and `tee`'s copy of the process's output append to the same log; the restart reads only the bytes appended
  after the attempt began.
- **Open question for the coordinator — the cap against the hang rate (as P9.1's Q12).** Stage 1 destroys 15,600 × 2 = 31,200
  engines, ≈ 10,400 per shard. At `DEFERRED` 104's rate (≈ 2 in 1,200), a shard expects **17.3 hangs**; Poisson: P(a shard
  needs more than 20 restarts) = **0.218**, P(at least one of the three stops at the cap) = **0.522**; and each hang idles 600 s
  before the cut — **≈ 2.9 h per shard** on top of ≈ 3.5 h of cells. At half that rate the cap is safe (P = 0.001; 1.4 h). At
  P9.3 A.7's under-load rate (1 in 27) the campaign is infeasible as specified. A shard stopped at the cap loses nothing — its
  records are on disk, and re-running its shard-mode line (no token) resumes it with a fresh count — but it needs the author.
  600 s and 20 are B.3's, implemented as written; a larger cap, a cap on consecutive cuts without progress, or a shorter
  timeout (60 s would still be 18x the slowest cell measured at G2) are the coordinator's to rule.
