## Answers to the brief's five task-specific questions

**1. Layout, and how a caller asks for "scenario S, draw D".**
```
scenarios/draws/<scenario_key>/draw_<NNNN>/{flow.json, cityflow.json, routes.rou.xml, provenance.json}
```
`<scenario_key>` is the **stem of the source sim config** (`cityflow1x1`, `cityflow_grid4x4`,
`cityflow_cologne3`) — identical to the `scenario_id` `collect.py` already writes into every manifest
(`offline/collect.py:518-523`), so there is no second registry to drift. `draw_<NNNN>` is zero-padded
to four digits, so lexical order equals numeric order across 0 / 1-999 / 1000-1099 and a pool is
greppable. The id is in the path *and* in `provenance.json`, and a test asserts the two agree.

Lookup is `draw_config_path(scenario_key, draw_id, out_root=...)` — **pure path arithmetic, no I/O and
no directory scan**, so the draw-cycling trainer can build its whole rotation up front. The written
config also carries the id visibly: `"flowFile": "../draws/cityflow1x1/draw_1000/flow.json"`.

**2. Did draw 0 round-trip byte-identically?** **Yes, on all three scenarios**, checked two ways.
In-test (`==` on bytes) and at the shell on the committed tree:
```
cityflow1x1:       IDENTICAL (3894236e5b8bacea47938fe2ca0e4c6a905e1f23e147c4f1a5e89f1ab8be1c08)
cityflow_grid4x4:  IDENTICAL (a872d1dd2ef0ce426c064ff521aac41eeb843f8087576517c5dad4691d4700e9)
cityflow_cologne3: IDENTICAL (4acf6970272c740dfc84864260aee409bb1828996de401e6b28443740c40f188)
```
Stronger still, on a real engine the draw-0 config reproduces the *source config's* 40-step MaxPressure
return exactly on all three: hz1x1 −760.00 vs −760.00, grid4x4 −103.00 vs −103.00, cologne3 −878.00 vs
−878.00.

**3. Evidence that two draws produce different trajectories under a deterministic policy.**
The load-bearing test materialises draws 1 and 2 for **hz1x1**, builds a real `CityFlowEnv` on each and
runs MaxPressure for 60 steps. It asserts three things, not one: both episodes ran the full budget,
draw 1 replayed against itself gives an **identical** digest, and draw 1 vs draw 2 gives a **different**
one. The self-comparison is what makes the inequality attributable to the demand rather than to engine
noise — and it is why the test runs on hz1x1, never cologne3 (your measurement: σ=3.3239 there).
Mutation A above shows the test goes red the moment two draws share a demand.

On the committed tree, at 40 steps: draw 1 vs draw 1000 returns are hz1x1 −573.00 vs −656.00,
grid4x4 −92.00 vs −124.00, cologne3 −450.00 vs −533.00. Across the whole tree, 33 draws have 33
distinct `flow.json` digests, and no training draw shares a demand file with a held-out draw.

**5. Anything §5's constraint makes harder, while it is still cheap to change.**
Nothing that I can see, and one thing deliberately made easier: `draw_config_path` does no I/O, so
"pre-construct one env per draw and rotate" costs one path join per draw. Two properties the trainer
brief should know: (a) the written `dir` is **absolute**, so a pre-built env is cwd-independent once
constructed; (b) draws for one scenario are siblings under one directory, so
`sorted((out_root/key).iterdir())` enumerates a rotation in numeric order. If the trainer would rather
address draws by a single flat key, say so now — a `<key>__draw_<NNNN>` flat layout is a two-line
change today and a migration later.

**What the next task will assume about this one**
- `draw_config_path(scenario_key, draw_id, out_root=DEFAULT_OUT_ROOT)` is a pure function returning the
  path of a runnable CityFlow sim config; `scenario_key` is the source config's stem.
- Draws **0-5 and 1000-1004** exist on disk for `cityflow1x1`, `cityflow_grid4x4`, `cityflow_cologne3`;
  materialising any further id is additive and never rebuilds an existing one.
- Draw 0 is the nominal control and is byte-identical to the shipped demand, so the draw-cycling
  trainer's mandatory "reproduces `_train_agent`'s per-episode returns exactly on draw 0" check has a
  materialised artifact to run against, not a special code path.
- Every draw is self-describing: `provenance.json` names the source sha256, the four randomiser
  constants, the pool and the draw id.
- **The tree is git-ignored.** A fresh checkout has no draws until
  `python -m offline.materialise_draws` is re-run; it reproduces byte-for-byte (verified: a full re-run
  reported all 33 draws `kept`).

**Limitations of what I shipped**
- SUMO route files are rendered but **not runnable** (no `.sumocfg`, P7.3) and must not feed a transfer
  measurement before P7.0's parity contract; hangzhou's inherits an unbound `<vType>`, recorded per draw.
- `grid4x4` has no SUMO rendering at all: its `.sumocfg` names `grid4x4.rou.xml`, which the repo does
  not contain. Recorded as `sumo_skipped_reason`, not silently omitted.
- The mutation barrier is proven for a build-phase failure and a commit-phase failure (injected). It is
  **not** proven against power loss or a full disk mid-rename; `os.replace` is atomic per rename, but a
  multi-draw commit is not one transaction.
- Only CityFlow sim configs are accepted as sources; a SUMO-native scenario has no path through this
  tool.
