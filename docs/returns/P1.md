**Deviations from the brief** (each with a justification)
- **`ix_ids` is stored in `env.intersections` order, not sorted.** The brief said "sorted once from
  `[ix.id for ix in env.intersections]`", but C1 says the action vector is ordered by
  `env.intersections`. Sorting would break the identity `ix{i}_action == action[i]` and require a
  remap table at every write site. Raised at GATE 1; the Master chat ruled native order correct and
  the brief wrong. Stated explicitly in the module docstring.
- **`Utils.reward_for_intersection` deliberately not used** (rule-5 exception). Its fallback chain
  (`agent/utils/utils.py:69-75`) substitutes the *global* scalar reward when `payload["reward"]` is
  absent — exactly the case the format requires to be `np.nan`. Using it would fabricate
  per-intersection rewards for envs with no `local_reward_fn`. `local_reward` is read directly from
  `next_info["intersections"][id]["reward"]`, key-absence → NaN. Verified and approved at GATE 2.
- **Two strengthenings beyond the brief**, both approved at GATE 2: `format_version` is stored inside
  each `.npz` (not only in the manifest) so the P2.4 linter can hard-fail per episode as C6:123
  requires; and an episode whose `lane_ids` disagree with the run-level `lane_ids_sha256` raises at
  `on_reset` rather than being left for the linter.
- **Episode digests use explicit little-endian views** (`"<i8"` / `"<f4"`) before `.tobytes()`. Native
  byte order would make `episode_sha256` platform-dependent and the P2.4 duplicate detector would
  disagree across machines.
- **`collect.py` exposes more flags than the brief listed** (`--control-mode`, `--global-reward-fn`,
  `--local-reward-fn`, `--global-reward-weight`, `--state-features`, `--metrics`, `--thread-num`,
  `--device`, `--libsumo`, `--map-file`, `--person-file`). The brief requires `run_metadata` to record
  the state features, reward-fn names and phase-control mode, which is only honest if they are
  settable. Defaults come from `experiments.config.SETTING_DEFAULTS` so collector and harness cannot
  drift.
- **Empty-lane-set guard added to `collect.py`** (GATE-2 amendment 1): `_require_lane_arrays` hard-fails
  after the first `on_reset` when `len(lane_ids) == 0`, with a message naming `--metrics`. The guard is
  in the collector, not the logger — the logger records `L = 0` honestly, because refusing to log is a
  collection-policy decision, not a format decision.

**Limitations of the format as shipped**
- **Reward-agnosticism is narrower than "any reward".** It covers rewards computable from the stored
  lane counts plus the scenario topology the manifest references — queue-family and PressLight-family
  both qualify. A reward that reads per-intersection metrics from
  `info["intersections"][j]["metrics"]` (available at `envs/base_traffic_env.py:478` but **not** stored)
  would require format v1.1. Master-chat ruling 2026-07-26: keep v1.0 global-metrics-only, record the
  narrowing explicitly. It is stated in the module docstring's layout section as well as here.
- **On SUMO and MOSS the lane dicts are `{}` when the metrics pipeline is off**
  (`envs/sumo_env.py:301`, `envs/moss_env.py:653`); CityFlow falls back to a direct engine query. The
  collector-side guard above turns this into a hard failure at collection time instead of a silently
  useless corpus.

**Conflicts found between brief and repo** (repo wins — what did you implement instead?)
- Brief/C2 present `info["metrics"]` as unconditional; both the global and the per-intersection forms
  are gated on the metrics pipeline (`envs/cityflow_env.py:279`, `envs/base_traffic_env.py:477`).
  Implemented with `.get("metrics", {})`; `metric_keys` freezes as `sorted(...)` at `on_reset`
  (mirroring `agent/MAPPOAgent.py:629`), an empty freeze is legal, and a mid-episode change raises.
- Brief describes `avail_mask` as coming from `Utils.extract_valid_actions`, which actually returns a

- `Utils.infer_action_counts` returns a positional `list[int]` and needs `env.action_space`, which only
  exists after `_setup_spaces()` (`envs/base_traffic_env.py:309`, called from `reset()`). It is
  therefore called in `on_reset`, not `__init__`, and via `getattr(env, "action_space", None)` so the
  `ix.num_phases` fallback path stays reachable.
- C6 stores `time_in_phase` as float32; the source is an `int` (`envs/phase_control.py:176`). Cast on
  write, documented.
- C3 sketches `MaxPressureAgent` under the `BaseAgent` API; it is not a `BaseAgent` subclass and its
  `act` takes only `info` (`algorithms/max_pressure.py:11,24,28`). The registry therefore holds
  per-policy adapter factories rather than one uniform call.

**A test was fixed during Phase 3 — disclosed in full**
`test_lane_id_order_preserved` failed after implementation. Per CLAUDE.md §0 I stopped instead of
editing it. Diagnosis: the test re-derived expected lane counts by constructing a fresh
`FakeTrafficEnv` and setting `_step_count`, but `FakeTrafficEnv._waiting()` also depends on
`_last_action.sum()`, which was `0, 2, 2, 2, 1` across the real run — so from row 2 the replay computed
a demand the run never produced. The logger had stored exactly what the env emitted, correctly
reindexed to lexicographic lane order. The Master chat verified the diagnosis and approved the fix; the
test now compares against `env.emitted_lane_waiting`, the dicts the env actually emitted, which removes
the risk that test and logger share a formula bug. Exact `==`, the `lane_ids == SORTED_LANES`
assertion and the column-order check are all retained; an additional `ep.lane_ids != RAW_LANES`
assertion was added. No assertion was weakened.
