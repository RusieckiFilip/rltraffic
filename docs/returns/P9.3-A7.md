## 3. A hang, and its cause — a finding for every CityFlow run under load
**What happened.** The first A.7 attempt stopped after 27 of its 60 episodes. Its log's last line was written at 13:17:05, and
nothing followed for more than 10 minutes. The process had **one thread**, waiting on a futex. Its CPU time stopped growing
(3.8 % averaged over its 693 s lifetime). With `PYTHONFAULTHANDLER=1`, a SIGABRT dumped its Python stack. The innermost frame
was `sweep_episode`, at the line that calls `probe_episode`, with no deeper Python frame: the block was inside a C++ destructor
running while the call's frame was torn down. The re-run of the unchanged command completed: 60 episodes, both T-regresses.
The aborted attempt wrote nothing, because the artifact is written last.

**The cause, read from the vendored source (`CityFlow/` is frozen; nothing was changed):**
- `Engine::~Engine()` (`CityFlow/src/engine/engine.cpp`) sets `finished = true` and then waits through six start/end barrier
  pairs for its worker thread.
- The worker's loop is `while (!finished) { … six phases, each a start/end barrier pair … }`, and `finished` is a plain,
  non-atomic `bool` (`engine.h`).
- The race: after the last `next_step()` both threads leave the final barrier. If the worker is descheduled and only reaches
  `while (!finished)` after the destructor has already set `finished = true`, it exits without joining any barrier. The main
  thread then waits on a two-party barrier forever.

**Measured in this session:**
- A live engine with `thread_num=1` runs **two** threads; a clean `del` brings the process back to one.
- The hung process had exactly **one**, in a condition-variable (futex) wait. That is the state the race leaves.

**Why it bites under load.** The worker has to stay unscheduled for the whole gap between the last step and the destructor:
- `probe_episode` and the harness's `evaluate_policy` free the engine within about a millisecond of the last step.
- `offline.collect` first writes the episode's compressed `.npz`, so its gap is longer.

The race also accounts for the pre-flight attempt that hung on 2026-10-15 (inside the canary's `run_probe`) and fits the
coordinator's hung test copies (A.1).

**What it does and does not do.** It hangs a process; it never changes a number, because every engine is deterministic and a
hung episode writes nothing. Paths that free an engine right after the last step are the most exposed: the gate, Phase B's
evaluation and the harness's evaluation episodes. The teachers' run completed (`Completed 5/5 cell(s).`, `exit=0`).

For `p93-corpus`, the amendment's liveness rule catches a hang (a process near 0 % CPU for 10 minutes). A hung collection
leaves a partly written `cf_hz4x4__*` directory, which the collector then refuses to reuse, so a re-run would need a ruling
first. I changed nothing frozen. Two options for the coordinator:
- run CityFlow-heavy steps when the machine is quieter;
- or authorise a fix to the destructor's shutdown handshake (for example an atomic `finished` and a handshake that does not
  depend on where the worker is in its loop).
