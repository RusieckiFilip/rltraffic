## §8 — task-specific questions

**Q1. The verified file-phase ↔ green-action mapping. Did it match `a+1`?**
**Yes, exactly `a+1`, and verified live rather than assumed.** Under `acyclic`, greens are the
file phases with duration > 5 (`[1,2,3,4,5,6,7,8]`; phase 0 is the 5 s clearance). Stepping a
real CityFlow env: action 0 → `current_phase 1`, action 3 → `current_phase 4`. The load-bearing
test `test_action_maps_to_file_phase_live` asserts `current_phase == greens[action]` across all
eight actions; `test_off_by_one_mapping_is_caught_live` proves a one-off mutation is caught, and
the mutation demonstration above shows it going red then green.

**Q2. k=3 vs k=4 numbers (entered/completed), and which you recommend and why.**
`cf_hz1x1`, CityFlow, acyclic, `dt=10`, `max_steps=360`, **episode-mean** `average_travel_time`
(the canonical measure — see the correction below), **seed 101, single run, nominal demand
(draw 0)**:

| config | clearance overhead | cycle | ATT (episode-mean) | entered | completed |
|---|---|---|---|---|---|
| k=3 | 16.67 % | 240 s | 235.90 | 1595 | 1440 |
| shipped plan (30+5) | 14.29 % | 280 s | 231.50 | 1623 | 1465 |
| **k=4 (recommended, ships)** | 12.50 % | 320 s | 216.92 | 1661 | 1506 |

**Recommend k=4** — as the Master chat ruled, by the **structural** criterion (clearance-overhead
fraction, computable before any simulation): k=4's 12.50 % is 1.79 pp from the shipped plan's
14.29 %, versus k=3's 2.38 pp. ATT-closeness would instead pick k=3 (|k3−shipped| = 4.4 vs
|k4−shipped| = 14.6), but selecting on an outcome is the pre-registered researcher-DoF trap; the
ruling rejects it deliberately. ATT is monotone in overhead and anti-monotone in cycle length,
identifying lost capacity from all-red clearance as the mechanism — no defect. `--fixed-time-k`
default is set to 4.

**Q3. Where fixed-time lands vs MaxPressure (160.56) and Random (307.53) on cf_hz1x1.**
Cleanly between, for every variant (episode-mean):
`MaxPressure 160.56 < k4 216.92 < shipped 231.50 < k3 235.90 < Random 307.53`.
Normalized return (random=0, MaxPressure=100): k4 ≈ 61.7, shipped ≈ 51.7, k3 ≈ 48.7 — a solid
middle rung. **MaxPressure reproduced to the cent (160.56) through this pipeline**, which is the
proof the measurement path matches the P0.2 anchors' path.

**Q4. t=0 offset and no-plan default; what else considered.**
*Offset:* cycle index 0 at step 0. The env resets to the first green, so step 0 emits action 0
(same green) with no spurious initial clearance, and the schedule starts on the shipped plan's
first green. Considered: a plan-derived or randomised offset — rejected as unmotivated for a
single intersection, but see the grid4x4 finding below, where a per-intersection offset is likely
needed. *No-plan default* (cologne1/3, grid4x4): equal split across the intersection's greens in
ascending action order, same k-step hold, clearance by the platform; cycle length =
`num_greens × 10k` s (grid4x4: 8 greens → 320 s at k=4). Recorded in the manifest as
`schedule_source="equal_split"`.

**Q5. Anything in §3's reasoning you think is wrong.**
§3's core reasoning is correct and I did not refute it: the k mechanism (`5 + (10k−5)` s per phase),
"do not change `delta_time`", and k-by-measurement all hold. Two things beyond §3:
(a) §4.4's `delta_time=5` faithful reference was impossible (already ruled — `phase_control.py:480`).
(b) **A measurement-aggregation confound I introduced and then caught — see the correction.** The
grid4x4 recheck also contradicts the "expect separation" expectation (finding below).

## Measurement-pipeline correction (important — corrects numbers I reported at the k gate)

At the plan/preview gate I reported k=3=309.60, k=4=285.42, shipped=300.91 and claimed "k=3 loses
to Random" and "fixed-time is near-random (beats Random by 6.6 s)". **Those were the *final*
`average_travel_time`, not the episode-mean the P0.2 anchors use** (`experiments/runner.py:175`
averages the per-step metric over the episode). The per-step ATT grows as travel accumulates, so
final ≫ episode-mean. Under the correct episode-mean aggregation (which reproduces MaxPressure
160.56 / 141.65 *exactly*): all of k=3/k=4/shipped sit cleanly between the anchors, and fixed-time
is **not** near-random on hz1x1 (≈ 76–90 s better). The k=4 ruling is unaffected because it rests
on the structural criterion, not on ATT. The committed `replay_plan` and the §9 gate now use the
canonical episode-mean, so replay numbers are comparable to k-runs and anchors by construction; the
gate still holds with **exact** equality (662.362637 both sides on the degenerate hold).

*How it was caught:* the anchor cross-check the Master chat instilled — MaxPressure via my pipeline
gave 247.75 vs the 160.56 anchor on the identical config, which forced the root-cause rather than
letting a plausible-but-incomparable number stand.

## Finding for P2.3 — the ladder inverts on grid4x4

`cf_grid4x4` (correct config `configs/sim/cityflow_grid4x4.json` — *not* `cityflow4x4.json`, which
is hangzhou_4x4_gudang), episode-mean, seed 101, draw 0:
`MaxPressure 141.65 < Random 207.26 < fixedtime-k4 232.23`. **Fixed-time is the worst of the three
— Tier 1 falls below Tier 0.** It is not gridlock (44 of 1473 stuck), just uncoordinated equal-split
fixed timing underperforming random on a coordinated grid. This contradicts the "expect separation"
expectation. Likely cause: the zero-offset no-plan default runs all 16 intersections in lockstep
(no green wave). A per-intersection **offset** parameter is the natural fix, but it is a design
change outside this brief — flagging for P2.3 / a follow-up, not implementing it unilaterally.
(Because C1 tiers are defined by *measured normalized return*, not policy names, an inverted rung is
a legitimate recordable outcome, but the reviewer-facing story needs it named.)
