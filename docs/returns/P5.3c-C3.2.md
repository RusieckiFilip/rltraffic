**`offline/context_sweep.py`** — its hunks are only: the two constants, `run_campaign_stage`, the new `_roll_round`,
and `run_reference_reroll_check`.
- **The constants:** `STAGE_RESULT_TIMEOUT_S = 180.0`, documented as about 30 × a cell's wall time under twelve workers
  (a result every ~0.5 s, ~6 s a cell per worker on 2026-09-30), and `STAGE_HANG_ROUNDS = 3`.
- **`run_campaign_stage`** runs rounds through `_roll_round`. Each round is one NEW spawn pool of the same size and
  initializer, read through `imap_unordered(...).next(timeout=STAGE_RESULT_TIMEOUT_S)`. On `multiprocessing.TimeoutError`
  the pool is terminated and joined, and then:
  - every `.cell_*.json.*.tmp` left in `cells/` is moved to `cells/failed/` by `move_aside`;
  - the round's cells with neither a result nor a chunk are the hung set, each printed as `  <name> HUNG (round n):
    re-rolled` and rolled again in the next round;
  - a cell that hung in the third round is a failure, `{"ok": False, "seconds": None, "error": "hung 3 times"}`, printed
    as FAILED.

  The return value gains `n_hung` and `hang_rounds`. A cell returning `ok False` is a failure as before, never re-rolled.
- **`run_reference_reroll_check`** reads its fifteen results the same way. After a timeout, every cell without a result
  is a failed roll: `HungRoll: no result within 180 s; the pool was terminated (DEFERRED 104)`, fenced in
  `failures.json`, the `RuntimeError` naming the kind only, exit 2. There is no retry there.

**The driver, header only:** §2's RESUME gains the HUNG-line sentence and the J1(c) restart, and §5 gains the cost of a
hung cell.

**NOT changed:** `_campaign_worker`, `run_campaign_cell` (P8.4b's path), the gate, the report, the artifact, `_cmd_cells`.

**Readings — flagged for the coordinator:**
1. **Rounds count pool runs, the first included.** A cell is rolled at most `STAGE_HANG_ROUNDS` = 3 times, and "hung 3
   times" means it hung in all three.
   - `HUNG (round n): re-rolled` is printed for n = 1 and 2.
   - `hang_rounds` counts the rounds that ended in a timeout: 1 in test (a), 3 in test (b).
   - If D.2.2 meant three RE-rolls after the first pool (four attempts), that is the loop bound and the error text.
2. **The re-roll check now reads unordered and pairs by name** (it was the ordered `imap` with a positional pairing check).
   - Under ordered `imap`, a timeout cannot tell the hung cell from those queued behind it, so the fenced record would
     name innocent cells and the count would be wrong.
   - The pairing guard stays: a duplicate or foreign name raises as before.
   - The verdict lines keep the declared order; the two existing re-roll tests pass unchanged.
3. **The tests' timeout is 5.0 s, not "≈ 2 s".** A fresh two-worker spawn pool's first result, its workers importing
   torch and the test module, measured 0.84, 0.92 and 0.93 s here, so 2 s would leave about 2× margin on a busy machine.
   5 s is still far below the fake hang's 30 s.
4. **`_cmd_cells`'s summary line does not print `n_hung`:** D.2.2 does not list it, and the HUNG lines are printed by the
   stage.

## 2. One C3.1 test changed — disclosed in full
- **Which:** `test_the_stage_pool_has_as_many_processes_as_workers` (C3.1, reviewer D's M3).
- **Why it had to change:** its fake pool's `imap_unordered` returned a plain `map`, and D.2.2(1) mandates reading
  results through `next(timeout=...)`, which a `map` lacks. On the implementation it failed with

  ```
          def imap_unordered(self, function: Any, tasks: Any) -> Any:

  ```
  They now return an `_InlineResults` whose `next(timeout=None)` yields the next result.
- **Unchanged:** the test's assertion. It still kills M3 at M3's new place in `_roll_round` (§4).
