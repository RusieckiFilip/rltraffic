## 2. The headline — it inverts the previous round's hypothesis

**The hang is NOT reachable against the committed code. The pin is what prevents it.**

The deadlock is a pre-existing `fork()` + libgomp hazard, not something this change introduces or
tolerates: a child entering an OpenMP parallel region with `nthreads > 1` waits forever on team
threads that `fork()` never duplicated. `torch.set_num_threads(1)` before the first parallel region
makes it run serially in the master thread, so there is nothing to wait on.

```
MODE=pin    PARENT_N=2   OK 0.02s      MODE=nopin  PARENT_N=2   HUNG 25.00s TimeoutError
MODE=pin    PARENT_N=16  OK 0.05s      MODE=nopin  PARENT_N=16  HUNG 25.00s TimeoutError
```

| invocation | mutant (pin neutered) | real committed code |
|---|---|---|
| threading file alone | `4 failed` — no hang | `4 passed in 2.42s` |
| smoke + T2 only | **`exit=124` — HUNG, killed at 120 s** | `11 passed in 3.87s` |
| smoke + whole threading file | **`exit=124` — HUNG, killed at 150 s** | `14 passed`, **10/10 runs** |

**Consequence for the plan: the pin is a liveness fix, not a performance fix.** The 5.80× / 1.37×
speedup is a side effect. That reframing is the single most valuable thing the review produced.

## 5. Assumptions the next phase inherits (plan §7 step 5)

What P2.1/P2.2/P5 will now silently rely on:

1. **`experiments/runner.py` is no longer byte-identical to `main`'s frozen copy.** One authorised
   +45-line delta. Any future task briefed as "the frozen set is untouched" is working from a false
   premise. `docs/patches/runner_thread_pinning.patch` is the durable record.
2. **Anything that imports `experiments.runner` and runs a cell pins *its own* process to 1 torch
   thread** — including `workers=1`. Intended, documented, but it is a **process-global side effect
   of calling a function**, and it escapes the runner. If P2.2's collection campaign or any P5
   training script imports `runner` for a helper, it inherits the pin whether or not it wanted it.
3. **Parallelism is safe *because of* the pin, not merely faster.** If any later task adds a code path
   that reaches `run_cell`'s work without passing the pin, it does not get a slow run — it gets an
   unbounded hang with no failure message, wedging both the suite and the PostToolUse guard.
4. **Corpus numerics are only bitwise-reproducible against a pinned run.** Anything collected or
   trained from here on is on the pinned side of an N2 float boundary. Nothing recorded predates it
   (no manifests in git), so the boundary is clean today — it stops being clean the moment a run is
   recorded from an unpinned path.
5. **`--workers N` is now worth using**, but budget at the **measured ~4×**, not 5.80×. P5's
   online-baseline budget: plan at ~4–6×, never 8×.
6. **Parallel and sequential produce identical aggregates** (`diff w1.log w6.log` → IDENTICAL, and
   the reviewer re-confirmed at smoke scale against a forced-16-thread run). P2.2 may therefore split
   collection across workers without a per-worker correctness caveat — on CityFlow. Not established
   for SUMO (see item 4 of §4).
7. **T2 self-skips when the start method is not `fork`.** On any platform that is not Linux-fork
   (macOS spawn, Windows), the pooled path has **no coverage at all** — only T1/T3 remain. Relevant
   if any of this ever runs off this box.
