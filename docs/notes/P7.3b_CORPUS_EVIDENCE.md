## 7. The manifest's git provenance — the coordinator's question, answered

**The 301–400 manifest does not lack git provenance, and neither manifest has it where it was looked
for.** `run_metadata` carries **no** `git_commit` and **no** `git_dirty` in *either* corpus; the two
manifests are structurally identical here.

`offline/trajectory_logger.py` writes exactly one git key, at **top level**, under a third name:

* `:303 _repo_git_hash()` — a bare `git rev-parse HEAD`, resolved against the module's own
  directory rather than the process cwd, so it records the revision of *the code*;
* `:467` captures it at logger construction;
* `:943` writes it as `"git_hash"` — a sibling of `run_metadata`, not a member of it.

| corpus | top-level `git_hash` | `run_metadata` git keys |

| `hz1x1_sumo_maxpressure` (201–300) | `8bf7eae7732275eb43e914f2e2b24fc40edfebdd` | none |

| the scratch re-collection | `f0eb121e2c373292c0522dda5bf5eca760db865a` | none |

⚠️ **There is no `git_dirty` anywhere in the corpus format, and there never has been.** `git_dirty`
is a *chunk* field, written by `transfer_curve._git_provenance` and refused by
`validate_cell_payload` (J1(b)); the corpus format has no equivalent, and `_repo_git_hash` does not
encode dirtiness in the hash either. **The evidence that the 301–400 half was collected from a clean

(`output/p7_3b_runs/collect_301_400.sh`), and `git status --porcelain` empty at `f0eb121` immediately
before the handover. Recorded as an open question for the coordinator rather than fixed here —
