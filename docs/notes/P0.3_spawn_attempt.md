# P0.3 — the `--workers > 1` "hang", diagnosed

**Updated:** 2026-07-28 · **Supersedes** the original "spawn does not work" note (kept as history in §7).

## Status: NOT REPRODUCIBLE — and the spawn patch is the wrong fix.

The reported `--workers > 1` hang was **never reproduced** on this machine.

- **Fork** completes the smoke config, and runs the **full `p0_baselines` config** (6 cells,
  60×360, `--workers 3`) for a full **20-minute window without hanging** — `faulthandler` caught the
  workers mid-`torch` forward/backward, not blocked on a lock. It did **not *complete*** in 20 min,
  but that is over-subscription slowness (§4/§5), not a deadlock.
- **Spawn** (the note's patch) completes the smoke config (1-cell and 2-cell, `--workers 2`)
  byte-identically to sequential. It was **not** run on the full `p0_baselines` config.
- The original symptom (frozen terminal, ~10% CPU) was never reproduced, and its stated mechanism
  (**fork cloning torch/CityFlow lock state**) is **refuted**: `experiments/` has **no module-level
  `torch` import**, so the parent has not touched torch at fork time (§3, H4).

**Cause unknown; most likely environmental** (WSL memory/thread state at that moment).
**Do not apply the spawn patch on the strength of the original note.** The real, *measured* problem
is thread **over-subscription**, and its fix is one line of thread-pinning — not `spawn` (§5).

Everything below was produced outside the repo (an rsync'd copy in scratch); `experiments/` was never
edited. `git diff --stat` on `experiments/` is empty.

## 1. Environment

Python 3.12.13 · Linux WSL2 · `multiprocessing` default start method = **`fork`** · 16 cores ·
`device` defaults to `"cpu"` (`experiments/config.py:54`), so CUDA is not in play.

## 2. Static facts (inspection, before running anything)

| Check | Result | Evidence |
|---|---|---|
| `run.py` has `if __name__ == "__main__":` | **YES** | `experiments/run.py:115` |
| `run_cell` is module-level (picklable by ref) | **YES** | `experiments.runner.run_cell`, qualname has no dot |
| Submitted args picklable **and** round-trip | **YES** | `pickle.dumps`+`loads` of `EnvSpec`, `agents` tuple, full arg tuple all succeed |

## 3. Hypothesis adjudication (H1–H3 from the original note, H4 added 2026-07-28)

| # | Hypothesis | Verdict | Why |
|---|---|---|---|
| **H1** | Missing `__main__` guard → spawn bootstrap `RuntimeError` | **REFUTED** | Guard present (`run.py:115`); spawn children bootstrapped and ran to correct results |
| **H2** | Unpicklable `run_cell` args → `PicklingError` | **REFUTED** | Direct pickle round-trip succeeds; spawn child executed the cell correctly |
| **H3** | Concurrent workers collide on output → corruption/hang | **REFUTED** (this config) | 2 cells × 2 spawn workers concurrent → both `ok`; report writing is deferred to the *main* process after all futures resolve; per-cell paths are unique; `saveReplay:false` |
| **H4** | Fork clones torch/CityFlow OpenMP/lock state → stall | **REFUTED (mechanism)** | Parent never imports torch before forking (§2); each child imports it *fresh*, so there is no inherited torch thread-pool state to be inconsistent. `thread_num=1` (`config.py:57`) → CityFlow is single-threaded per worker. |

**H4 has a live descendant that is NOT a hypothesis but a measured fact:** the ~16 cores seen pegged
under `--workers 3` are 3 children each spawning torch's default OMP pool (= core count) → ~48 threads
on 16 cores. That is **over-subscription** (§5), the real performance story.

## 4. The control experiment — DO NOT re-attribute the roadnet error to spawn

The literal command `run.py smoke.json --workers 2`, run from the **wrong working directory**, fails
with `cannot open roadnet file → KeyError: 'road_0_1_0_1'`. This is a **CWD artifact**, not a spawn
bug: the CityFlow sim config resolves `"dir": "scenarios/…"` relative to the process CWD, and the
canonical invocation is from the repo root.

Proof it is CWD, not spawn — same scratch copy, same directory:

| run | CWD | result |
|---|---|---|
| `--workers 2` | scratch copy | ❌ `cannot open roadnet file` |
| `--workers 1` (control) | scratch copy | ❌ **same** error (so it is not workers/spawn) |
| `--workers 1` | repo root | ✅ `Completed 1/1` |
| `--workers 2` (spawn) | repo root | ✅ `Completed 1/1`, numbers identical to seq |
| `--workers 2`, 2 cells (spawn) | repo root | ✅ `Completed 2/2`, both `ok` |
| `--workers 2`, 2 cells (**fork**, repo runner) | repo root | ✅ `Completed 2/2`, identical numbers |

Keep this row set. The `cannot open roadnet file` error is the single most plausible thing the
original P0.3 attempt saw and mis-blamed on spawn — but the original error was never recorded, so this
is a lead, not a claim.

## 5. Scaling benchmark — the finding that actually matters for the budget

Reduced `p0_baselines` (train_episodes=**10**, 2 env × 3 seed = **6 cells**, max_steps 360, MAPPO
rollout 1024), repo **unpatched fork** runner, 16 cores, serialized runs, warm caches:

| workers | unpinned wall | speedup | pinned wall (`OMP=MKL=OPENBLAS=1`) | speedup |
|---:|---:|---:|---:|---:|
| 1 | 339.7 s | 1.00× | 247.7 s | 1.37× |
| 3 | 1165.3 s | **0.29×** | 76.3 s | **4.45×** |
| 6 | ≥1200 s (hit cap) | ~0.28× | 58.6 s | **5.80×** |

(Speedup vs `workers=1 unpinned`. All finishing runs wrote **6/6 `ok`** cells — no hang, no failure.
The `workers=6 unpinned` run hit the 1200 s cap and was killed; its `cells_ok` reading is unreliable
because `results.json` is only written at the very end. It was CPU-pegged throughout, i.e. thrashing,
not deadlocked.)

Two hard conclusions:

1. **Unpinned `workers > 1` is a REGRESSION.** `workers=3` unpinned is **3.4× slower** than a single
   worker; `workers=6` unpinned never finished. Every worker grabs `nproc` OMP threads → 48–96
   threads fighting over 16 cores. The project's parallel path, as currently shipped, makes things
   worse, not better. This — not any deadlock — is the closest thing to the "it falls over" report.
2. **Thread-pinning is the real lever, and it works.** `workers=6` pinned = **5.80×**; even
   `workers=1` pinned is 1.37× faster than unpinned (tiny nets don't want 16 threads).

### Impact on the P5 budget (this changes planning)

The plan assumed an **8× parallel multiplier that nobody had measured**. Measured reality:

- The honest multiplier is **~4–6×, and ONLY with thread pinning.** Without pinning it is **< 1×**.
- `workers=6` pinned = 5.80× vs the unpinned single-worker baseline (the likely basis for the
  15–60 h estimate) → **~3–10 h**, not 15–60 h. Against a *pinned* single-worker baseline it is 4.23×.
- Plan on **~4–6×**, not 8×, and treat **thread pinning as mandatory** for the online-baseline phase.

The one-line fix is `torch.set_num_threads(1)` in `run_cell` (or exporting `OMP_NUM_THREADS=1` in the
launcher) — **not** the spawn patch. It touches frozen `experiments/runner.py`, so it is an **open
question for a future brief**, not applied here.

## 6. Two facts that change other planning

- **SUMO / libsumo fork-safety is a KNOWN UNKNOWN, parked for P7.** libsumo/TraCI are in-process
  native engines and a plausible fork-safety hazard under `workers > 1`; this benchmark only exercised
  CityFlow. SUMO collection isn't needed until the P7 transfer study, so defer — but re-test the
  parallel path on a SUMO-backed config before relying on it there.
- **P2 corpus collection needs no worker pool at all.** `offline/collect.py` uses **no
  multiprocessing** (verified). Parallelise P2 by launching **N independent shell processes, one
  `--out-dir` each**: `trajectory_logger.py` already enforces one out-dir per process ("One `out_dir`
  belongs to one process", `trajectory_logger.py:304`; a populated out-dir is refused without
  `--overwrite`, `:341`). `runner.py`'s pool is only for the online-baseline *training* phase.

## 7. History — the original "spawn does not work" note (2026-07-26)

The original attempt switched `ProcessPoolExecutor` to `mp_context=mp.get_context("spawn")` to stop
`--workers > 1` "falling over", tested it manually, saw it "not work", and **did not record the
error**. This update reproduced that exact patch and command: **it works.** The 2026-07-26 conclusion
was drawn from an unrecorded, non-reproducible failure — most likely the CWD/roadnet artifact (§4) or
the over-subscription slowdown (§5) misread as a hang.
