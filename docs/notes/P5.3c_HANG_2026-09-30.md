## The mechanism (`CityFlow/src/engine/engine.cpp`, `CityFlow/src/utility/barrier.{h,cpp}`, vendored and FROZEN)
- The engine runs `threadNum` controller threads (here one); every simulation phase is a `startBarrier.wait()` /
  `endBarrier.wait()` pair on two-party barriers (`Barrier(threadNum + 1)`); the controller loops `while (!finished) { … six or
  nine phases … }`, checking `finished` — a plain `bool` — only at the loop head.
- `Engine::~Engine()`: `finished = true;` then `for (i < (laneChange ? 9 : 6)) { startBarrier.wait(); endBarrier.wait(); }`, then
  `thread.join()`. It assumes the controller is inside its loop and will run exactly one more iteration.
- **The race:** after the episode's last `nextStep()`, the controller returns from its last `endBarrier.wait()` and, before it
  evaluates `while (!finished)`, can be descheduled. If the Python side reaches the engine's destruction in that window (the
  episode's record, the env's close: milliseconds later), the controller reads `finished == true`, exits its loop and its thread
  ends. The destructor then calls `startBarrier.wait()` on a two-party barrier with one party: **`pthread_cond_wait` forever,
  inside CityFlow, with no engine thread alive** — the dump above, and the single-threaded canary of 2026-09-29 (`DEFERRED` 101:
  one episode, then the destructor). The window is a few instructions wide, hence the rate (two in roughly 1,200 episodes on this
  machine today, both under load: twelve workers with CUDA service threads on sixteen CPU threads; the canary during three
  concurrent test loops).
- **What it means for the numbers:** nothing. The hang is at the END of an episode, after every quantity of the cell exists in
  memory and before the chunk is written (the write is atomic, so no partial chunk); the engine is seeded (engine seed 1000), so a
  re-rolled cell reproduces the same values — the reference gate's `==` on 500 cells is the standing proof of that reproduction.

## The remedy (Amendment D.2, C3.2): at the stage, not in the engine
`run_campaign_stage` consumes `imap_unordered` through `next(timeout)`; a result that does not arrive within the timeout terminates
the pool (the hung worker dies on SIGTERM), moves any worker's `.tmp` aside, and re-rolls the cells without a chunk in a fresh pool,
up to three rounds; the same timeout in the fenced re-roll makes a hung re-roll a failed roll (exit 2, nothing consumed). The cell's
own path — P8.4b's — is untouched. `DEFERRED` 104 records the engine's race for the platform's maintainers; `CityFlow/` is frozen
and is not patched here.
