**⚠️ CLAIM CONSTRAINT — action masking (measured 2026-08-07, before the claim was written).** The
corpus is collected under `control_mode: acyclic`, whose `available_actions()` returns **every** green
phase, so **`avail_mask` never binds anywhere in our data: 460/460 per-intersection streams are
entirely `True`.** This is binding on what C1/C2/C3 may say. Masking stays in the architecture — the
env raises on illegal actions, masks bind under cyclic and RESCO-cyclic modes, and P6's lane closures
are designed to make them bind — but on **this** corpus a no-mask ablation measures nothing, and no
paper sentence may credit masked-action modelling as a learned capability or as a source of our
performance. Making masking a *result* requires a corpus collected under a mode where it binds: a new
collection, not a re-analysis. Found by the P3 implementer in pre-flight, which is the only cheap time
to find it — after the claim is drafted it costs a retraction.

**Named method component:** *probe-calibrated return prompting* — target RTG expressed relative to a cheap
in-domain probe policy (MaxPressure) return distribution (e.g., quantile-space). One mechanism serving
both C2 (infeasible-RTG under scenario shift) and C3 (reward-scale shift across backends), with its own
ablation. ⚠️ **NOVELTY NARROWED 2026-08-01:** DTLight already sets RTG as `max_offline_return × scale`
(γ_eval = 0.2, γ_online = 0.3) *with its own ablation figure*, explicitly to avoid hand-setting RTG per
agent. So "scale-factor RTG conditioning **within** a domain is taken." Our defensible remainder: RTG
calibrated **in the target domain** from a probe policy run there, for the cross-backend case DTLight
never faces (it never transfers between simulators). Position precisely against their Fig. 4 or a
reviewer will call it a re-run.

**Controversy framing (the paper's hook) — SHARPENED 2026-08-01 after reading both primary sources:**
DataLight (2303.10828) states DT "cannot be applied for TSC", but its Appendix A.5 shows the negative
result rests on a configuration that is not a fair test of sequence modeling: **context length K ∈ {1, 2}
only** (K=1 is *no* sequence modeling), and **a single hardcoded RTG of −351** for all agents and
scenarios. Their DT scores 779–1295 s ATT against ~240 s for good methods, and "DT performs better
under K=1 than K=2" — consistent with a model that never had enough context to model anything.
DTLight (2312.07795) with a proper DT (GPT-2, 6 layers/8 heads teacher) beats all online baselines on
5–6 of 8 scenarios **purely offline**. So the contradiction is real but *explicable*, and our two
mechanisms are exactly the two DataLight omitted: context length (P5.3 ablation) and calibrated RTG

## 2. Hardware & Compute Budget

- **GPU:** NVIDIA RTX 5080 (ample VRAM for DT training; 7–8B local LLM in 4-bit for the optional teacher extension)
- **RAM:** 64 GB — sized for large offline trajectory corpora held in memory during training
- **CPU:** high-end multi-core — the actual bottleneck is simulation; data collection parallelizes across CPU workers (one env per process)
- **Strategy:** simulators are CPU-bound → generate the offline corpus in parallel overnight; DT training is pure supervised learning → GPU-efficient, fast iteration. This asymmetry is *the reason* the offline approach fits our hardware.

Repo: `github.com/RusieckiFilip/rltraffic` — the June 2026 UW bachelor's thesis of Bibrowski, Bublik, Pisula & Woliński (sup. G. Grudziński), lineage RESCO → RESCO TensorCell → this framework. - **Three simulator backends, one API:** CityFlow (vendored, patched for Python 3.12+), SUMO (traci/libsumo), MOSS (GPU). Agents/rewards/metrics/states are backend-neutral.
- **Agents present:** DQN, DQNAgentPFRL (RESCO parity), IPPO, MAPPO (centralized critic + running normalization). Baselines: MaxPressure, random. *(Corrected 2026-08-05: this line previously read "fixed-time via phase-control modes" — false. ## 4. Interface Contracts (FROZEN — paste into every sub-chat brief)

### 4.1 Environment API (non-standard Gym — do not "fix" it)
```python
info = env.reset(seed=42)                                (# returns info ONLY, no obs)
reward, terminated, truncated, info = env.step(action)   # reward FIRST
```
`action` is an `np.ndarray`, one action per intersection, **ordered by `[ix.id for ix in env.intersections]`**.

### 4.2 The `info` dict contract
```python
info = {
    "sim_time": float, "vehicle_count": int, "step": int,
    "average_travel_time": float,
    "lane_vehicle_count": {lane_id: int}, "lane_waiting_vehicle_count": {lane_id: int},
    "metrics": {metric_name: float},                # requested global metrics
    "intersections": {
        ix_id: {
            "state": [...],                          # per-intersection obs vector
            "avail_actions": [0, 2],                 # legal actions NOW (masking!)
            "current_phase": int, "time_in_phase": int,
            "action_applied": bool,
            "metrics": {name: float},
            "reward": float,                         # ONLY if local_reward_fn set
        }, ...
    },
}
```

### 4.3 Agent API (mirror `agent/MAPPOAgent.py`)
```python
class MyAgent(BaseAgent):
    def __init__(self, gym_env, ..., device=None, seed=None)   # reads env.intersections
    def act(self, info, explore=True, update_memory=True) -> np.ndarray
    def observe(self, next_info, reward, terminated, truncated=False) -> dict
    def save(self, path); def load(self, path)
```
Helper functions in `agent/utils/utils.py` (USE THESE, do not reimplement):
`Utils.infer_action_counts(env.action_space, intersections)`, `Utils.extract_per_intersection_info(info, ids)`, `Utils.state_from_info(ix_payload)`, `Utils.extract_valid_actions(ix_payload, n_actions)`, `Utils.scalar_reward(reward)`, `Utils.reward_for_intersection(...)`, `Utils.resolve_device(device)`, `Utils.seed_everything(seed)`.

### 4.4 Coding standards
Python ≥3.12, PyTorch, type hints (`from __future__ import annotations`), numpy `float32` for stored arrays, docstrings in the repo's style, no new heavy deps without a Decisions-Log entry, `pytest` tests for everything, no modifications to `envs/base_traffic_env.py` unless a task explicitly says so.

## 5. Offline Data Design (agreed v0.1 — refine in P1/P3)

- **Format:** one `.npz` (compressed) per episode + one `manifest.json` per collection run.
- **Per step, per intersection:** `state (float32)`, `action (int64)`, `avail_actions mask (bool, width = n_actions)`, `local_reward (float32, NaN if unset)`, `current_phase`, `time_in_phase`.
- **Per step, global:** `global_reward`, `vehicle_count`, `sim_time`, selected `metrics`.
- **Episode metadata:** scenario id, backend, engine seed, `delta_time`, `max_steps`, `state_features` list, reward fn names, phase-control mode, behavior-policy id + checkpoint hash, repo git hash, timestamp.
- **Dataset ladder (C1's experimental axis; released publicly as a contribution, positioned vs DTRL):** tiers are defined by **measured normalized return** (random = 0, MaxPressure = 100, computed per scenario post-collection), NOT by policy names — our own P0.2 data shows MaxPressure > MAPPO@60ep, so policy names imply a false quality ordering (critique 2026-07-11b). Source policies (= dataset provenance metadata): random, fixed-time, MaxPressure, MAPPO checkpoints (60/200/converged), ε-noised MAPPO (ε ∈ {0.1, 0.3}), DQN(CNN), mixed. The paper's ladder table reports the measured return distribution of each dataset. If no learned policy beats MaxPressure after convergence, the top slice IS MaxPressure — which sharpens, not weakens, the "does MADT exceed its data" question.
- **Demand randomization is mandatory for every collected episode (P2.0):** with deterministic CityFlow flows, N episodes of a deterministic policy = 1 trajectory × N; effective corpus size of deterministic tiers ≈ 0 (critique 2026-07-11a). Each episode = (scenario, flow-draw seed); nominal flow = draw 0. Randomizer operates at the vehicle-list level (verified: flow.json = per-vehicle insertions with routes) so draws render to BOTH backends (flow.json ↔ .rou.xml) — preserves C3's paired scenarios and fixes P8's environment-stochasticity problem at the source. Logger convention: flow-draw id goes into run_metadata (no logger code change needed).

## 7. Sub-chat Protocol (hardened 2026-07-12 — designed for AI-written code)

Threat model: the dominant failure mode of AI-heavy development is *confident code with a silent semantic bug that nobody independently checked*. Every rule below exists to catch that.

**Execution modes.** Coding tasks preferably run in **Claude Code** on the user's terminal inside the repo (reads real files, runs real tests); chat sub-chats remain the fallback. Briefs carry a mode header: in Claude Code the "attach files" list becomes "read these repo paths", and these guardrails apply: work ONLY on a task branch (`task/<id>-<name>`), NO edits to existing repo files unless the brief says so, commit before finishing, Return Packet includes the actual `pytest` output and `git diff --stat`.

**Lifecycle per task:**
1. Master chat issues the **Brief** (self-contained; embeds §4 contracts; Definition of Done; ≤ ~2 source files + tests — larger tasks get split).
2. Implementation sub-chat (Claude Code preferred) writes code + tests on the task branch, ends with the **Return Packet**.
3. **Critical-path tasks get an independent review sub-chat** (fresh context; receives brief + contracts + diff; finds discrepancies ONLY, writes no features; may run in Claude Code read-only). Critical path = anything the paper's data flows through: trajectory logger, flow randomizer, dataset/RTG loader, DT agent, corpus linter, statistics harness. Merge to main only after review passes.
4. User pastes Return Packet(s) back → Master chat updates checkboxes, issues next brief.
5. **Phase-boundary review:** before freezing any phase, Master chat writes down what that phase assumes about later phases (this caught determinism↔corpus and reward↔RTG couplings late; do it early now).

**Stopping rule for review rounds (added 2026-07-25).** A review round is worth running while it can
still find *load-bearing* defects — things that would force rework (a wrong data format, a missing
baseline, a confounded experiment). Once a round returns only style and preference items, stop and ship:
further rounds trade real progress for churn. Planning documents get **at most one** external review
round, then they freeze. From P1 onward the review function moves into the pipeline (P1.5-style
independent review of an actual code diff against a frozen spec), which is bounded by construction —
reviewing code against a fixed contract terminates; reviewing prose against opinions does not.

**One writer per working tree (added 2026-08-07).** While an implementer session is live in the same
directory, **the coordinator does not commit.** `git checkout -b task/...` switches the branch for
*every* session sharing the tree, so a coordinator commit silently lands on the implementer's branch.
**Check `git rev-parse --abbrev-ref HEAD` before any commit.** If both must write, use a worktree.
⚠️ **And `git push origin main` from a task branch is a no-op that reports success** — it pushes the
unmoved `main` ref, not your work. *Recorded after three coordinator commits landed on
`task/p2.6-format-v11` and three "pushed" confirmations were false; the §10 handoff the user had been
told to restart against was neither on main nor on the remote.*

**End every Master-chat turn with exactly one decision line (added 2026-08-07).** One of two forms,
verbatim, as the final line of the message:

```
DECISION NEEDED: <what> | my recommendation: <what> | reversible: yes/no
NO DECISION NEEDED — continuing with <next thing>.
```

**Reserve `DECISION NEEDED` for choices that are irreversible or that touch the paper's claims**;
everything else is decided and reported. The `THINGS YOU NEED TO DO:` block goes immediately before
this line. *Recorded 2026-08-07 after discovering the format existed **only in the conversation** —
the rule that references "the closing decision line" had been written down while the line itself
never was, so a fresh session would have produced the block and not the line.*

**Surface every human action in a fixed end-of-turn block (added 2026-08-06).** The Master chat ends
every turn with `THINGS YOU NEED TO DO:` — numbered, copy-pasteable — immediately before the decision
line, and writes `nothing` when there is nothing, so its absence is never ambiguous. Anything the user
must run, apply or restart appears there in full even if it was already named earlier. **A required
action mentioned only in prose is an action that does not happen** — the agent-definition patch sat
unapplied for a day because it was introduced mid-message.

**A brief's acceptance criteria are claims too (added 2026-08-07).** Any acceptance criterion in a
brief that asserts a **property of real data** must either **cite the measurement that established
it** — with its sample — or be **marked unverified and handed to the implementer to check before it
becomes a test**. BRIEF_08 specified "`average_travel_time` is monotone non-decreasing early in an
episode"; that was reasoning presented as fact, and 407 of 407 real episodes falsify it (the metric
averages over completed *plus currently-active* vehicles, so an entering vehicle pulls the mean
down). **`scripts/check_test_hygiene.sh` cannot catch this: it greps tests, and this was upstream of
any test existing.** The guard has a blind side exactly where specifications enter, and this is the
project's signature error one layer earlier in the pipeline than we had been watching.

**A fixture that satisfies the assertion by construction is a tautology, not a fixture (added
2026-08-07).** `FakeTrafficEnv` hardcodes `average_travel_time: 12.5`, and a constant satisfies
"monotone non-decreasing" — so the falsified criterion would have shipped **green**. Any fixture
backing a load-bearing test must be built so the **wrong implementation is detectable**:
non-constant where the property is about change, and differing values where the property is about
*which key was read*.

**Campaign scripts must abort and must self-verify (added 2026-08-06).** Every multi-command
collection or training script gets `set -e` **and** a final assertion that completed collections
equal collections requested. The 2026-08-06 ATT campaign had neither: one tier was refused by the
out-dir guard, fifteen-plus raised `ValueError`, and the loop ran on to a clean-looking end. Run
overnight it would have reported success with half the corpus missing.

**Check the output directory before issuing a collection command (added 2026-08-06).** The
populated-`out_dir` guard exists and we designed it; a command that trips it wastes the slot.

**An inertness or equivalence check must enumerate its cases before it runs (added 2026-08-06).**
State which cases exist and which were tested, in the message that reports the result. "Adding a
metric does not change trajectories" is a claim about seven behaviour policies; it was tested on
one and was false for four of them.

**Verify runtime state before asserting it (added 2026-08-06).** Before any instruction that assumes
a job is running or finished, check `ps` or the file count in its out-dir. The coordinator twice
reported on the state of a run it was not watching, and planned two turns of work around a campaign
that had died an hour earlier.

**A corrected definition propagates in BOTH directions (added 2026-08-07).** When an amendment changes
what a quantity *means*, it must be propagated **forward** to future measurements **and backward to
every conclusion already recorded under the old meaning**. Concretely, and mechanically: **any
`PREREGISTRATION.md` amendment that changes a quantity's definition requires, in the same turn, a grep
of this plan for conclusions resting on the old meaning, and each hit is either re-derived or marked
`NOT SETTLED`.** A1 was propagated forward — P8.0 re-derived the P0.2 anchors — and never backward,
and the expensive casualty was not a number in a table but a **finding steering P4/P5**: "the ladder's
expert tier is scenario-dependent", whose grid4x4 and cologne3 margins are 2.5 % and 5.8 % against a
40 % measured legacy-vs-horizon gap. Fixing a metric is not fixing the results computed with it.
*Applied to the existing amendments the moment it was written, which is the only honest way to add it —
otherwise the rule would itself have been propagated forward and not backward. Two hits: (1) **A2**
retired two illustrative figures on 2026-08-06 and §3.1 still carried them a day later, in the section
every phase is anchored against; (2) **A4** makes `vehicle_count` at the horizon a mandatory companion
to every ATT cell and **no recorded ATT cell carries one** — folded into queue item 0, since both are
`[-1]` of arrays the corpus already stores.*

**Deleting a test is permitted ONLY when its specification was withdrawn (added 2026-08-07).** This project had never sanctioned a test deletion before P2.6 removed three that asserted amendment A4's now-withdrawn validity condition. It is the right call — **keeping a test for a retired specification is worse than deleting it**, because it pins a withdrawn rule into the suite and the next session will "fix" correct code to satisfy it. But *"the spec changed"* is also the most available excuse for deleting an inconvenient test, so the permission is fenced mechanically. **All three conditions, every time:** (a) the withdrawn property must be retired by a **written, dated authority** — an amendment, a ruling — **cited by name in the commit message AND the Return Packet, never left to a diff**; (b) the net test count must not fall; (c) **the withdrawal must itself be pinned** — add an assertion that the retired thing is *absent from the module surface*, so a partial revert cannot reinstate it through a docstring edit or a stray constant. Condition (c) is P2.6's invention (`test_no_validity_threshold_survives_anywhere`), offered unprompted, and it is the part that makes deletion safe rather than merely defensible.

**A rule has a SCOPE, and applying it outside that scope is a failure of the same kind as ignoring it inside (added 2026-08-07).** Every prior instance in this log is **under**-application — a rule not applied where it should have been. P2.6's refusal to rebase its own branch is the first **over**-application, and it matters because **from the inside the two are indistinguishable**: both feel like caution and refusal to act unilaterally, and over-application is the harder of the two to catch because it looks like diligence and nobody challenges it. **Diagnostic, one question: name the party this rule protects, and check that party is present in the case at hand.** The one-writer rule protects *other sessions sharing a tree*; a session rewriting its own branch as sole writer was never in scope. Cost of getting it wrong in this direction is real and invisible — here it would have forced a hard-conflicting merge across four duplicated commits instead of a clean rebase. **The fix for over-application is the opposite of the fix for under-application**, which is why the two are named separately rather than filed together as "apply rules carefully".

**A check must report its DISCRIMINATING POWER, not only its pass rate (added 2026-08-07).** Any
identity or invariant used to **certify data** must state, beside its pass rate, the distance between
the correct answer and a deliberately wrong one — the same quantity on the misaligned, mis-keyed or
mis-scaled variant it exists to reject. §7 already forbids tests that *cannot fail*; it had nothing to
say about checks whose *force* was never measured. The corpus-alignment identity separated right from
wrong by **108×** on grid4x4 and by **1.8×** on cologne3: rigorous in form, nearly empty in force, and
on cologne3 it would have certified the corpus while being unable to detect the error it was written
for. A pass rate answers "did it agree"; only the margin answers "would it have noticed". Report both,
or the check is decoration.

**Verify by EFFECT, not by STATUS (added 2026-08-07).** A command whose success output is identical
whether or not it did anything must be verified by its effect on the artifact, never by its exit code
or its report. `git push origin main` from a task branch pushes the unmoved `main` ref and reports
success — three false confirmations, indistinguishable from true ones. The fix generalises: compare
the refs, not the exit code. Same shape as `claude_guard.sh` exiting 0 after a commit (its verdict is
evidence about `git status`, not about the working tree), as the ten inert `Write(...)` permission
rules that looked protective, and as a green suite whose corpus tests all skipped. **Where success and
no-op are observationally identical, the status line is not evidence.**

**Grep the plan before escalating a decision (added 2026-08-06).** Before marking anything
`DECISION NEEDED`, search `docs/PROJECT_PLAN.md` for an existing answer — the frozen claims in §1 and
the task checklist in §6 most often hold one. If escalating anyway, say where you looked: *"I checked
§1 and §6; there is no answer there."* This is the same discipline as verifying the artifact instead
of its description, applied to our own plan. Re-litigating a settled design spends the one resource
the coordinator cannot regenerate — the user's attention — and risks a fresh answer that silently
contradicts a frozen one.

**Fix the class, not the sentence (added 2026-07-31).** When a false claim is found, the correction
must be applied to every claim of the same shape, not only the one that was caught. This project has
now produced five instances of the same failure — a claim measured on a sample and stated about the
population: Master chat's "≥7 paired scenarios" (from a `.sumocfg` referencing a missing file),
Master chat ticking off P0.3 (from a commit message rather than the code), Master chat's fabricated
"8× parallel speedup", the sub-chat's "8305/8305 entries, every flow file in this repo" (four files),
and — after writing the retrospective about that very error — "startTime is sorted ascending in every
file checked" (false for two files) and "interval is int in hangzhou" (hangzhou_4x4 is float).
**Rule: a measured claim must state its sample, or measure the population.** When correcting one,
grep for its siblings in the same document before declaring it fixed.

**Suppressed-assertion guard (added 2026-07-31, after `assert X or True` shipped undisclosed).** A
mechanical grep must run over `tests/**` in the guard hook and reject always-true assertion patterns:
`or True`, `assert True`, `assert 1`, `if False:`, bare `pass` in an `except`, `pytest.skip` without a
reason, `pytest.raises` without `match=` on a test whose name claims a specific error. Rationale: the
CLAUDE.md §0 rule ("never edit a test to make it pass — stop and say so") worked twice in the same task
and failed once, silently. A rule that depends on remembering is weaker than a grep. This is the same
philosophy as the frozen-file guard: mechanical enforcement beats good intentions.

**Filesystem-mutation barrier (added 2026-07-31, after the pattern recurred).** In any collection or
data-producing tool, **every filesystem mutation — writes AND deletions — must happen after all
validation, never before**. This bug has now appeared twice in the same shape: P1's NB2 (`--overwrite`
deleted the previous corpus before constructor validation, so a failed construction destroyed data and
only then raised) and P2.0 (both draw materialisation and `_clear_stale_draw_files` ran before the
logger's populated-`out_dir` check, so a refused run could write files and delete a previous run's
demand). The fix in both cases was ordering, not new logic. Reviews of P2.5, P3 and P2.4 must check
this explicitly.

**Redundancy rules (non-negotiable):**
- **Double computation of critical quantities:** RTG in the loader verified by an independent `np.cumsum` test path; logged rewards vs rewards recomputed from per-lane counts — equality asserted on real episodes; randomizer dual-backend renders checked for equivalence.
- **Corpus linter (P2.4) after every collection run:** manifests, shapes, NaNs, reward-recompute equality, return distributions, **episode-hash duplicate detector** (residual guard on the determinism failure mode).
- **Sanity anchors:** any phase producing numbers compares against §3.1 (P0.2) before results are accepted.
